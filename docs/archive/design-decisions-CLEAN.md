## 一、架构总则

### 1.1 内容 vs 引擎：绝对分离（用户硬性要求）

```
引擎层（core，零题材词汇）
  └─ mechanism primitive 注册表（小、稳定、与题材无关）

内容层（content/）
  ├─ config/elements.json              七系
  ├─ config/element-combinations.json  稀疏有序组合表
  ├─ config/effect-params.json         primitive 参数 schema
  ├─ config/displayTiers.json          显示档位 50 档区间映射
  └─ effects/*.json                    效果 = primitive 组合 + 参数
```

**引擎只读 `components[].primitive` 与 `params`，永不读 `displayName`。**

效果声明式示例（灼烧）：

```json
{
  "id": "eff-burn",
  "displayName": "灼烧",
  "textKey": "burn",
  "components": [
    { "primitive": "damage-over-time",
      "params": { "ticks": 3, "perTick": 12, "element": "fire", "tickTiming": "turn-start" } },
    { "primitive": "visual-flag", "params": { "flag": "burning" } }
  ],
  "stacking": { "mode": "refresh", "maxStacks": 1 },
  "dispel": { "dispellable": true, "resistance": 0 },
  "expiry": { "mode": "turns", "value": 3, "onDeath": "clear" }
}
```

### 1.2 primitive 体系（共 11 个）

| 类别 | primitive | 说明 |
|---|---|---|
| **MVP 使用（9）** | `damage-over-time` `instant-damage` `stat-modifier` `rate-modifier` `crit-modifier` `dodge-modifier` `visual-flag` `heal` `dispel` | `heal`/`dispel` 与 `instant-damage` 同族（都是"对某目标施加一次效果"），加进来不破坏结构 |
| **MVP 只注册不使用（2）** | `armor-modifier`（作用于外功防御） `action-lock` | 作为抽象层压力测试 |

**参数统一用通用结构**：`amount` / `duration` / `targetSelector` / `condition`。所有可编辑项（ticks、dispellable、resistance、expiry、stacking、onDeath、`chance`）全是数据，参数 schema 在 config，编辑器据此自动生成表单。

**`instant-damage` 是 Round 10 补的关键 primitive**——此前"攻击造成伤害"被当作战斗默认行为未建模。补上后四个用法共用一套代码：

| 用法 | target |
|---|---|
| 普通攻击 | 敌方 |
| 自伤（燃血） | 自身 |
| 反伤 | 攻击者 |
| 溅射 | 相邻目标 |

**扩展性代价表**：

| 未来想做的事 | 需要改什么 | 动引擎吗 |
|---|---|---|
| 加第 8 系 | `elements.json` 加一项 | 否 |
| 删掉一系 | 删一项 + 迁存档 | 否 |
| 加一个新组合 | 组合表加一格 | 否 |
| 加一个新效果（用现有 primitive） | 加 effect JSON | 否 |
| 加一种全新伤害模式 | 注册新 primitive | **是**（只加模块，不改已有代码） |

### 1.3 数值化原则：数字 + UI 映射表

> 用户原话："引擎里就直接写成等级，我只是要你在 UI 上显示武侠风，这样它只是一个映射关系，明白吗！我在外面删不删档位，跟你等级一毛钱关系没有，只是要修改映射关系。"

```
引擎 core  ──→  数字等级 (level: 3)
存档        ──→  数字等级 (level: 3)
UI 映射表   ──→  "高手"        ← 改词、增删档位只动这里
```

于是：
- **改名称**（高手 → 好手）：只改映射表，引擎与存档都不动
- **删一档 / 加一档**：只改映射表，引擎与存档都不动
- **改档位划分**：只改映射表

**唯一需要迁移的例外**：改**等级上限**（如境界 6 级 → 4 级）。此时越界的存档要收敛，属 `ADR-0002` 版本化迁移。这不是"改映射"，是"改量程"。

**四条技术约束**：
1. 序列定义为 `content/config/` 里的**数组**，引擎只遍历
2. 引擎代码**不出现序列长度字面量**（不能有 `for i in 0..6`）
3. 引擎与存档**只存数字等级**，武侠词是 UI 层的映射
4. 数值→档位的映射是**配置表**（`displayTiers`），不是硬编码阈值

**映射表结构**（Round 20 推广）：**key 是数值，value 是一个配置对象**——`label` 只是其中一个字段，下游规则、解锁清单、呈现参数都在同一处。

```json
{
  "rarity": [
    { "level": 0, "label": "寻常", "affixCount": { "min": 0, "max": 0 }, "hasSpecialAffix": false },
    { "level": 1, "label": "精良", "affixCount": { "min": 1, "max": 2 }, "hasSpecialAffix": false },
    { "level": 2, "label": "罕见", "affixCount": { "min": 3, "max": 4 }, "hasSpecialAffix": false },
    { "level": 3, "label": "绝世", "affixCount": { "min": 5, "max": 6 }, "hasSpecialAffix": true }
  ]
}
```

引擎读对象里的字段，**永远不读 `label` 做判断**。校验器需检查：区间无缝、无重叠、覆盖全值域、**下游规则自洽**（如稀有度递增时词条数下限不得递减）。

### 1.4 引擎绝不按枚举的具体值分支

**真正标准（Round 19.4）**：不是"有没有语义"，而是**引擎是否按具体值分支**。

| | 引擎行为 | 后果 |
|---|---|---|
| ❌ 反例 | `if (element === "fire") { ... }` | 加第 8 系要改代码 |
| ✅ 正例 | `apply(config.elements[elementId].modifiers)` | 加第 8 系只加 config 一项 |

**把分支条件数据化，是让枚举可增删的关键**。例：内功/外功要走不同防御——不写 `if (source === "internal")`，而是：

```json
{ "id": "external", "defenseStat": "armor" }
{ "id": "internal", "defenseStat": "innerDefense" }
```

引擎读 `defenseStat` 字段，不按 id 分支。加第三种作用方式只需加一条 config。

**加 vs 删的不对称**：

| 操作 | 安全性 | 需要做什么 |
|---|---|---|
| **加成员** | ✅ 安全 | 加 config 项即可 |
| **删成员** | ⚠️ 需谨慎 | ① 校验器检查引用；② 处理已有引用（内容条目 + 存档）→ `ADR-0002` 迁移 |

删除的成本不在引擎，在**引用完整性**。

**必须 id 化的三类**（引擎或内容会硬引用）：
1. **primitive 类型**——引擎按 id 找实现
2. **内容条目**（武功、装备、怪物、兽、门派、脉）——`content.md:30`
3. **事件类型 / 命中类型**（命中/暴击/闪避/反伤）——引擎按 id 分支

### 1.5 形状 vs 逻辑（评估待定项的方法论）

| | **形状（shape）** | **逻辑（logic）** |
|---|---|---|
| 是什么 | 存档结构、抽象层次、扩展点、枚举契约 | 具体业务规则的实现代码 |
| 改了的后果 | **动架构 + 数据迁移** | 只改一个函数／模块 |
| 例子 | 事件流字段、primitive 契约、效果实例运行时状态 | 离线致死用哪条规则、掉落权重怎么算、波次调度怎么排 |

**用法**：评估任何待定项时，先问"它动的是形状还是逻辑"。形状 → 现在必须定；逻辑 → 可后定，**前提是它被封装成可替换的边界**。

### 1.6 三条判断原则

1. **原则一（用户 Round 10 明确）**：内容可以后补，**形状不能**。凡是"将来加功能需要重写引擎"的地方，现在就要把抽象做出来——即使该功能本身不做。
2. **原则二（Round 17 提出、Round 18 修正）**：**名称与数量都是内容，引擎不得写死**。可以"有几层"，但改了数量不能崩。
3. **原则三（Round 24）**：**凡是可能变化的业务规则，都要留一个可替换的边界**（策略函数／配置表／钩子）。这样它就永远是"逻辑"问题，而不会升级成"形状"问题。

三条的关系：原则一告诉你**什么必须现在定**；原则二告诉你**什么不能写死**；原则三告诉你**怎么保证其余的东西永远不必现在定**。

## 三、战斗系统

### 3.1 完整形态

| 层 | 进攻侧 | 防御侧 |
|---|---|---|
| **战斗形态** | **支持多目标（1vN）**，1v1 为特例 | `targetSelector` 需支持 单体／全体／相邻／随机 N 个／除主目标外 |
| **作用方式** | 内功 / 外功（招式字段；怪物攻击也标） | **外功防御** / **内功防御** — 2 个属性 |
| **系别性质** | 七系（附加伤害 = 兵刃层 × 系别系数） | 怪物亲和度（config） + 效果抵抗（条件修饰符） |
| **伤害构成** | 兵刃层（恒有）+ 系别层（可有可无） | — |
| **减伤公式** | — | 百分比 + 递减 `减伤 = 防御 / (防御 + K)`，K 在 config |
| **组合** | 主（武功/门派）× 辅（装备）→ 有序查表 | — |
| **资源** | 招式消耗内力 | 内力上限（境界 + 心法 + 装备） |
| **命中判定** | 闪避判定 → 命中（**不做招架/格挡**，留 v2） | 闪避率：通用低基调，基础 5-10%，上限约 40%，递减曲线在 config |
| **出招意图** | **intent 源可插拔**（MVP 仅 `auto-source` = 加权轮盘；未来注册 `manual-source` 即支持主动释放，core 零改动） | — |

**伤害构成为什么必须是两层**：

```
一次攻击的伤害 = 兵刃层（无属性，恒有，受外功防御减）
              + 系别层（附加的效果与伤害，可有可无）
```

三个理由：① 用户原始设想里"门派武功无属性"是三种情形之一，没有兵刃层无法表达；② 纯兵刃流应是合法构筑，不该是"什么都没配"的残废状态；③ 让属性成为**附加层**而非**替代层**，换装备不会让既有构筑失效。

附加伤害 = 兵刃层 × 系别系数（config 里 7 个数），不需要 7 套公式。

### 3.2 伤害计算管线（12 阶段）

> `ADR-0005:6` 的"固定值 → 加法百分比 → 乘法区"是**修饰符的聚合规则**，不是**伤害的应用顺序**。这两件事必须分开定义，否则"破防和火系加成谁先算"会变成糊涂账。

```
1.  基础值      base          招式/装备/境界的原始数值
2.  固定加成    +flat         "火系伤害 +50"
3.  百分比加成  +add%         "火系伤害 +15%"（同类相加）
4.  乘法加成    ×mult         "所有伤害 ×1.2"（异类相乘）
5.  暴击        crit          暴击率判定 + 暴伤倍数
6.  攻方修正    source        内功/外功各自走对应防御
7.  守方减免    defense       外功防御 / 内功防御（百分比递减）
8.  易伤/抗性   vuln/res      目标受伤加深、系别亲和度
9.  闪避判定    dodge         0 或 1
10. 最终值      final
11. 后续触发    post          反伤、吸血、溅射、兽的追加
12. 应用        apply         扣血 → 判定致死 → 触发致命保护
```

第 12 步含**应用前拦截点**（致命保护在此插手）。

⚠️ **必须现在定死**：① 它是所有数值平衡的地基；② 每个 modifier 都要声明自己作用于哪个阶段；③ **后改会让所有已配数值失效**。

### 3.3 七系表（定稿）

**核心设计选择：相克不要做成"削弱"，要做成"变异"。** 理由：传统"水克火 → 火系伤害 -30%"会让玩家觉得构筑踩雷，是纯负反馈，与 `ADR-0001`"流派由玩家玩出来、不预设标签"相悖——踩雷的构筑没人玩，等于预设了唯一解。

**为什么是七系**：五行（5 个）构成闭环，每个元素必须克一个、被一个克。**加到 7 个，闭环就断了**，没有现成的相生相克表，组合规则必须显式声明——这正好把"相克削弱"赶出去，只留"变异"。

| 系 | 轴 | 主位效果 | 辅位修饰 | 内力性格 | MVP 形态 |
|---|---|---|---|---|---|
| 金 | 破防 | 裂伤（受伤加深）、破防 | 锐化：加深、转即时 | 耗内破防 | 纯数值 |
| 木 | 疫毒 | 中毒、传染 | 蔓延：扩散、叠加速 | 寄赖/吸内（**需代价**） | **真状态** |
| 水 | 滞缓 | 冰寒（降频）、治愈(v2) | 流转：范围化、传导 | 滋养：回复/上限 | 纯数值 |
| 火 | 燃爆 | 灼烧、爆裂（溅射） | 爆裂：溅射、转爆发 | 倾泻：高耗高爆发 | **真状态** |
| 土 | 守护 | 护体（减伤）、稳固(v2) | 沉滞：延时、固化 | 承载：上限/代偿减伤 | 纯数值 |
| 风 | 迅疾 | 疾（提频）、连击(v2)、闪(v2) | 迅发：提速、连击化 | 轻灵：消耗降低 | 纯数值 |
| 雷 | 霆爆 | 暴（暴击）、震(v2)、瞬(v2) | 震荡：触发式、追加 | 激荡/背水（**需代价**） | 纯数值 |

**Round 3 对前五系的三处调整**（为消除轴重叠）：
- **金的「流血」→「裂伤」**：流血/中毒/灼烧三者都是持续伤害，三重重叠。改为"裂伤"（目标受到的所有伤害提高）后，金独占**破防/增伤**轴。
- **木的「缠绕」→「传染」**：木（缠绕降频）、水（冰寒降频）、风（疾提频）三系抢同一根"频率"轴。木去掉缠绕，专注**疫毒**轴。频率轴留给水和风，一降一升形成对称。
- **土的「稳固」／水的「治愈」／风的「连击、闪」／雷的「震、瞬」留 v2**。

**两系新血的差异化**：风是**己方增益**（提速），与水（敌方降频）对称；雷是**瞬时爆发**（暴击），与火（持续燃烧 + 范围）对称——火是"烧一阵、烧一片"，雷是"一下很疼"。

**关键**：七根轴（破防／疫毒／滞缓／燃爆／守护／迅疾／霆爆）恰好是 **2 个真状态 + 5 个纯数值**，加两系未增加状态系统负担。

### 3.4 主辅有序组合

> **主属性（来自武功/门派）决定这一招"是什么"**——提供该系的核心效果。
> **辅属性（来自装备）决定这一招"额外怎么样"**——对核心效果施加一个修饰。

用户洞察："水武功+火装备"与"火武功+水装备"产生的效果应该不同——这把组合表从 49 格**对称**矩阵变成**有序**矩阵（同系那 7 格除外）。

**这解决了"全部相生会不会导致最优解唯一"**：辅属性不是"谁都行，越多越好"，而是七种修饰**方向不同**，取舍来自方向而非强弱。

组合查表是稀疏的（不必填满 49 格），未定义的组合走各系的默认修饰。

### 3.5 内功 / 外功（作用方式）

- 内功/外功 = 伤害的**作用方式**（打皮肉筋骨 vs 打内腑真气）
- 七系 = 伤害的**性质**（火、毒、寒……）
- 是 **2×8 矩阵**（8 = 七系 + 无属性），不是二选一

**价值**：① 防御从 1 个变 2 个，成本极低（+1 属性），却给怪物设计"外功型 Boss / 内功型 Boss"的分类；② 非常武侠；③ 与招式/心法不冲突也不重复。

**命名**：**外功防御** / **内功防御**（用户 Round 7 定，Q19）。⚠️ 防御属性的旧名「护甲」已废弃，一律称「外功防御」。

**内力与内功防御不硬挂钩**：武侠直觉诱人，但一旦挂钩，堆内力同时拿到"更多招式 + 更高防御"，易成唯一解。想要联动就走内容层词缀（"内力上限的 X% 转化为内功防御"）。

### 3.6 防御侧：为什么不做七系抗性

**决策：外功防御 + 内功防御是唯一通用减伤，不设玩家侧分系抗性。**

一旦设火抗/冰抗，就要面对七个新属性——七条词缀线、七套装备底材、怪物表七个字段、UI 七个读数，以及 7×7 攻防平衡。

**体感来源拆解**（用户混淆的两件事）：

| 体感来源 | 需要什么 | 成本 |
|---|---|---|
| 不同系的伤害颜色/飘字/文本不同 | 配色表 + combat-text 按系分池 | 几乎免费 |
| 不同系带不同效果 | 效果系统 + primitive | 中等 |
| 打火系怪时火系伤害明显变小 | **怪物侧**一个字段 | 很小 |
| "我这身火抗堆到 75%"的成长感 | **玩家侧** 7 个抗性属性 | 巨大 |

**前三条的降本关键 = 把差异放在怪物侧**：

```
monster: { id: "mon-fire-toad", affinities: { fire: -50, water: +30 } }
dungeon: { id: "dun-blaze-cavern", affinities: { fire: -30 } }
```

玩家体感完全一样，但工作量是一个字段 + 一次查表。且**亲和度可按内容量线性铺开**（只给 Boss 和特色怪设，普通怪为 0），抗性系统做不到这点。

**双向博弈的完整形态**：

| 方向 | 进攻方 | 防守方 |
|---|---|---|
| 玩家 → 怪物 | 系别层伤害（兵刃层 × 系别系数） | 怪物**亲和度**（config） |
| 怪物 → 玩家 | 系别层伤害（同理） | 玩家**抗性**（条件修饰符） |

**玩家侧抗性用"条件修饰符"而非"属性"**：

```
词缀「耐火」= stat-modifier {
  target: damage-taken,
  condition: { source: { element: "fire" } },
  amount: -20, unit: "percent"
}
```

| | 属性式抗性 | 条件修饰符式抗性 |
|---|---|---|
| 角色 schema 字段 | 7 个 | **0** |
| 存档新增数据 | 7 个数 | **0** |
| 加第 8 系 | 加字段 + 迁存档 | **加 config 一项** |
| 词缀内容线 | 7 条 | 7 条（**真成本，跑不掉**） |

**形式不对称是有意的**：怪物侧用 config（设计者直接指定的关卡参数，不需要成长曲线）；玩家侧用条件修饰符（玩家需要成长与配装，必须是走聚合管线的动态值）。

**代价**：① 7 条词缀线是硬成本；② 抗性需要上限（`-75%`，走乘法区递减）；③ UI 上玩家看不到"火抗 30%"的明确数字，需额外做聚合读数；④ 平衡工作量回来了。

**POE 抗性讨论的结论（同意用户，并推得更远）**：

> **产生选择压力的从来不是"玩家的防御属性"，而是"怪物身上的系别特征"。**

证据是暗黑 2：同样有抗性上限，但暗黑 2 有**免疫怪**——地狱难度某怪火焰免疫，用火系就是 0 伤害，必须换系。同一个抗性系统，**加了"怪物侧免疫"这个变量，抗性就从门槛变成了选择**。而"怪物对某系免疫/高抗"正是**怪物亲和度**要做的事。

即：**给玩家 7 个抗性属性 → 门槛；给怪物系别亲和度 → 选择。** 同样的体验目标，后者成本是一个 config 字段。

**七系的爽感来源**（正面回答用户追问）：

| 来源 | 强度 | 成本 |
|---|---|---|
| **发现搭配**（火+风=蔓延、火+水=蒸汽） | 最强 | 组合表（内容） |
| **视觉/文本**（火焰焦黑、中毒青紫、冰寒结霜） | 很强 | 配色表 + 文本分池，几乎免费 |
| **效果在做不同的事** | 强 | 效果系统，已在方案 |
| **数字手感**（火系一下很大、风系密而小） | 中 | 系别系数，7 个数 |
| **打特定秘境换系明显更轻松** | 中 | 怪物亲和度，一个字段 |
| **我的火抗堆到 75% 了** | **最弱** | **7 个属性 + 7 条词缀线** |

**核心结论：抗性不产生爽感，抗性产生的是"站得住"的资格。** 压力不能没有——抗性的正确定位是"够用即可"。

### 3.7 七系在防御侧 = 效果抵抗

```
减伤层：外功伤害 → 外功防御减        内功伤害 → 内功防御减
效果层：火系 → 灼烧              抵抗「抗灼」→ 不被点燃 / 持续时间减半
```

四条理由：① 效果才是七系的灵魂；② 走条件修饰符，复用 ADR-0005，加系不改 schema；③ 比抗性数字更有戏剧性（"我吃了避毒丹" vs "我的毒抗是 60%"）；④ 与内功/外功二分完全兼容。

### 3.8 闪避

- **只做闪避，不做招架/格挡**（留 v2）。命中判定两级：闪避 → 命中。
- **通用低基调**：基础 5-10%，上限约 40%，递减 `实际闪避 = 闪避 / (闪避 + K)`（与外功防御、抗性同一族公式），K 在 config。
- **闪避只让这一次攻击落空，不跳过回合**（否则高闪避拖成无限战斗，破坏秘境循环节奏）。
- **闪避是纯数值，不是状态** → 不破坏"2 真状态 + 5 纯数值"的平衡。
- **离线结算**：期望值，`有效输出 = 原始输出 × (1 − 闪避率)`。
- **与风系不绑定**：闪避是通用数值，风系只通过**内容层词缀权重**更容易出闪避词缀，引擎不知情。
- **降低闪避**：`dodge-modifier` 对目标施加负值。土（压）／木（缠，走传染线）／水（滞）三种语义均可。

**三条硬约束**：
1. 上限与递减必须有（闪避边际收益非线性：50% 闪避 = 生存时间翻倍，75% = 四倍）。
2. 闪避只让这一次攻击落空，**不跳过回合**。
3. 闪避是**纯数值**，不是状态。

**用户洞察**："降低闪避比提高闪避更有趣"——堆闪避是自己变强，降低闪避是**破解对方构筑**，给 PvE 一个"这 Boss 闪避高，我得带压制手段"的解法维度。

**注意**：木的「缠绕」已移至 v2（为把频率轴让给水）。木要承担"减闪避"，走**传染**那条线顺带表达，或走词缀而非系别效果。**不为减闪避把缠绕拉回 MVP**——那会重新引入刚消掉的重叠。

**兑现既有承诺**：`ADR-0006:6` 已写"命中类型（暴击/闪避/反伤）"；`style-guide.md:32` 已写"暴击 / 闪避 / 反伤 / 中毒 各有专属模板池"。这不是新增需求，是兑现已承诺未兑现的条目。

### 3.9 内力系统

**放置游戏特有的坑**：自动战斗 + 可离线，玩家不在场时谁管内力？

➡️ **模型 A：持续回复**。按秒回内力，边放边回；离线用**稳态 DPS 公式**（收支平衡点），**O(1)** 结算。手感是"爆发—调息—爆发"，最武侠。

**内力耗尽怎么办**：必须定。放置游戏里"没内力 = 打不出招"最挫败。➡️ **零消耗的基础攻击**（拳脚），内力见底自动切换，输出下降但不归零。

**内力上限来源**：境界 + 心法 + 装备词缀，全部走 ADR-0005 管线，引擎不写死公式。

**七系 × 内力映射表**：

| 系 | 内力维度的性格 |
|---|---|
| 金 | 耗内破防：消耗额外内力换取无视部分外功防御 |
| 木 | 持续寄赖：中毒需持续供内力维持，或转为**吸内** |
| 水 | 滋养：内力回复加快 / 上限提高 |
| 火 | 倾泻：高消耗换高瞬时爆发，容易见底 |
| 土 | 承载：上限提高 / 受击时内力代偿减伤 |
| 风 | 轻灵：消耗降低 / 出手频率提高 |
| 雷 | 激荡：消耗换暴击；或**内力越低伤害越高**（背水） |

**MVP 只进最小形态**（上限 + 消耗 + 持续回复 + 零消耗基础攻击），七系 × 内力差异化留 v2——**但代价设计已定**（见 3.10）。

**xkx100 印证**：`内力保有上限 = 基本内功级别 × 15`，即**内力上限是派生资源**。我们的设计与之同构且更简，方向一致，不必改。

### 3.10 代价设计（吸内 / 背水 / 自伤）

两者都**攻击了内力系统的根基**：吸内让对方失去出招能力，背水让玩家有动机维持空内力——都会让"内力"这个刚建起来的资源失去意义。代价必须补回这个意义。

**木系 · 吸内 —— 四重代价叠加**：

| 代价 | 机制 | 为什么 |
|---|---|---|
| 不能吸干 | 目标内力不会降到上限的 25% 以下 | 保证对方永远还能放低耗招——否则是锁死，不是压制 |
| 转化效率低 | 吸 100 点，自己只进账 40%，其余消散 | 主要价值是削弱对方而非给自己充电，否则变成续航神技 |
| 自身伤害低 | 携带吸内的招式伤害系数 ×0.7 | 用伤害换资源压制，一笔明确的交易 |
| 可被抵抗 | 走效果抵抗机制（「固本」类词缀） | 给了克制手段，避免成为必选 |

净效果：吸内是**压制型**路线——打不疼人，但让对方越打越没招。强在节奏破坏，不强在数值。

**雷系 · 背水**：

```
触发：内力 < 30% 时开始生效
加成：伤害 ×(1 + 最大加成 × 衰减系数)，最大加成 +50%（config）
```

| 代价 | 机制 |
|---|---|
| 门户大开 | 外功防御同步下降（伤害 +50% 时防御约 −25%） |
| 闪避降低 | 背水时不留余地，闪避率按同比例下降 |
| 需要主动维持 | 内力会自动回复，维持低内力必须持续消耗——不是被动状态，是玩家自己撑住的钢丝 |

净效果：**玻璃大炮**——输出最高、死得最快，且要求配装与招式循环都围绕"把内力花光"设计。有动机成本，不是白拿。

**自伤换增益**（七伤拳先例——崆峒派"伤人七分，自损三分"）：

| 代价 | 机制 |
|---|---|
| 无视外功防御 | 自伤是精血损耗，不走防御计算——堆防御无法抵消 |
| 无视护体 | 同理，`stat-modifier` 减伤对它无效 |
| 可致死 | 自伤能把自己打死（否则可无脑压血） |
| 触发濒死档 | 自伤后的剩余生命档进入文本选择——你可能把自己写进"颓然倒地"那一档 |

最后一条的双重价值：自伤不只在数值上有代价，**在叙事上也有代价**。

**是否绑定系别：不绑定**。自伤是通用机制，任何系都能有"燃血"词缀。硬塞给火系会重蹈"闪避绑定风系"的覆辙（破坏一系一轴）。

**共同原则**：代价不是"数值打折"，而是"在另一个维度上付账"。保留两个流派的极端手感，只给每个极端配一个真实软肋。全部参数（吸取率、下限阈值、效率、伤害系数、背水阈值、加成上限、防御衰减比）在 config，引擎零写死。

**代价数值后置**（用户明确）：所有代价参数在 config，调整数值不改引擎；连机制本身也能扩展（新的代价形式 = 新的 primitive 组合或新的 condition）。现在写下的任何数字都不是承诺，只是初值。

### 3.11 出招与 intent

**出招 = 加权轮盘，不是排序**：

```
每次出手时机 → 在可用招式中按权重随机抽一个
权重 = 基础权重 × 所有命中的调制器
```

**MVP 4 个调制器**：

| 调制器 | 效果 |
|---|---|
| 冷却 | 冷却中权重归零 |
| 内力 | 不足则降权/归零 |
| 重复衰减 | 刚放过 → 临时降权（避免三连同一招） |
| 系别亲和 | 装备/武功系 → 同系升权 |

**留 v2**：条件加成（目标某状态 → 某类升权）、连携表（上一招 X → 下一招 Y 升权）。

引擎只有一个通用"加权轮盘"机制，所有规则是数据。

**MVP 一个招式 = 一个条目，不做多形态**，改用更便宜的方式兑现丰富度：**一个招式配多条文本变体，随机抽**。（xkx 的"每个武功一系列招式"其实是同一招在不同武功等级有不同形态，我们没有"武功熟练度"且 Avoid「等级」。）

**intent 源可插拔**：

```
战斗循环（core）：
  1. 收集 intent（谁、用什么招、对谁）
  2. 校验（冷却 / 内力 / action-lock 等状态）
  3. 执行 → 产出事件流
  4. 推进时间

intent 来源（可插拔）：
  ├─ auto-source：加权轮盘        ← MVP 唯一
  └─ manual-source：玩家输入队列   ← 未来补，注册即可
```

**core 只认 intent 接口，从不问来源。**

**intent 三维度可独立配置**（Round 22 关键发现）：

```
intent = {
  actor:   谁释放    ← auto
  skill:   用什么招  ← auto（权重轮盘）| manual（玩家点招式）
  target:  对谁      ← auto（targetSelector）| manual（玩家点目标）
}
```

| 形态 | skill | target | 说明 |
|---|---|---|---|
| 纯自动 | auto | auto | 当前默认 |
| **半自动**（用户要的） | **auto** | **manual** | 系统出招，玩家指定打谁 |
| 全自动 | manual | manual | 玩家点招式 + 点目标 |

**主动释放武功的扩展性（用户硬性要求）**：先不完全排除主动释放，只是先不做，后续随时可补，**不在引擎里预先限制**。

**是否现在在 schema 加 `activation` 字段 → 不加**，理由是区分两件事：
- **架构维度抽象**——"谁决定出招"是战斗循环必然存在的环节，做成可插拔不是预留，是设计正确。**这个现在就做。**
- **为不确定的功能预留数据字段**——`activation: auto | manual` 是给未设计的功能开字段，会在每个招式条目里躺着直到（也可能永远不）用上，正是 `ADR-0004:7` 反对的预留。

将来真做时，加字段成本由版本化存档迁移（ADR-0002 已定）承担。

**手动目标选择的动机**（用户提出）："如果一个技能的属性是随机单体目标，但本层需要先秒掉某个关键怪，怎么办？"——**随机单体 + 需要先杀关键怪 = 玩家失控**。

⚠️ **由此引出的矛盾**：离线时没有玩家输入，target 只能走 auto。➡️ **解法：玩家配置"目标优先级策略"**（"优先精英"／"优先残血"／"优先最高威胁"）。离线时按此策略选目标，战术意图被保留。这是**策略配置**而非实时操作，符合放置品类。

**引擎要求**：`targetSelector` 支持三来源，优先级 **③ > ② > ①**：① 招式自带（内容声明）；② 玩家策略配置（存档，离线用此）；③ 实时玩家点击（仅在线）。

### 3.12 时间与随机

**时间模型**：招式按"冷却"自动释放 → 战斗是**实时推进（tick）**，非回合制。所有冷却、DoT 跳数、状态持续都挂在 tick 上。离线结算 = tick 快进 + 稳态公式。

**随机性来源（穷举）**：出招权重、暴击、闪避、词缀 roll、掉落、文本选择、兽出场、致命保护。

→ **每一处都要回答"离线时怎么办"**。统一策略是"在线掷骰、离线期望值"，**但致命保护是例外**（0/1 事件，期望值失真）。

**离线致死的三个解法**：
- **A. 离线战斗不致死**（✅ 采用）：离线秘境推进不会让角色死亡，最多"推不动了"；致命保护离线时不参与计算。
- B. 保守模型：假设保护未触发，若致死则判定推进失败。安全但偏严。
- C. 离线按 CD 就绪与否确定性判断：不掷骰，CD 好了就算触发。可预测但在线/离线规则不一致。

选 A 的理由：放置游戏的离线结算本就该是"稳的"，让死亡成为离线结果会让玩家不敢离线，与放置品类核心体验冲突；在线时该机制照常掷骰，严肃性未丢。

## 四、战斗文本

### 4.1 槽位全集（13 个 + 闪避专用 4 个）

**语法 = `{attacker}` 英文花括号**，**不是** xkx 的 `$N/$n/$w/$l`（`research:264` 自己建议不要照搬 `$` 记号）。

**已删**：`{动词}`（动词应是模板固定文本，槽位化导致句式雷同，违背 `style-guide.md:46`）；xkx 代词 `$P/$p`（`style-guide.md:8` 已要求"同一集合内视角一致"，视角是集合级常量）。

| 槽位 | 说明 |
|---|---|
| `{attacker}` `{defender}` | 攻方 / 受方 |
| `{move}` | 招式名 |
| `{weapon}` | 攻方兵器 |
| `{defenderWeapon}` | 守方兵器 |
| `{limb}` | 被击部位 |
| `{damage}` | 伤害数值 |
| `{consequence}` | 后果文本（从四档词库抽出后嵌套填入） |
| `{elementFlavor}` | 系别意象（无属性时填**中性词，不可为空串**，否则产生"，，"） |
| `{opening}` | 起势 |
| `{moveIntro}` | 招式引出 |
| `{weaponAction}` | 兵器动作 |
| `{verb}` | 动词 |

> 后四个是 Round 10 片段化后新增的。引擎眼里它们与前九个完全相同（都是"从词库按条件取一条"）。❓ 是否分为"填空变量 9 + 可选修饰 4"两类描述，见 12.2。

**闪避专用 4 个**：`{dodgeSubject}` `{dodgeManner}` `{dodgeMove}` `{dodgeAftermath}`（见 4.5）。

### 4.2 模板 = 片段序列，非"一句固定话挖洞"

```
{opening}{attacker}{moveIntro}「{move}」，{weaponAction}{elementFlavor}，
{weapon}{verb}{defender}的{limb}，{consequence}。
```

| 片段 | 词库示例 | 选择依据 |
|---|---|---|
| `{opening}` 起势 | ""、身形一晃、沉肩坠肘、脚下步法一变、深吸一口气 | 节奏档 |
| `{moveIntro}` 招式引出 | 使出一招／一招／倏然施出／缓缓递出／猛地挥出 | 品阶 + 节奏档 |
| `{weaponAction}` 兵器动作 | ""、剑身剧震、剑光急速穿梭、在半空折返划出一道弧光、剑锋嗡鸣 | 品阶 × 暴击 |
| `{elementFlavor}` 系别意象 | 剑锋赤红，热浪逼人／周身腾起一层赤焰／空气被灼得微微扭曲 | 系别（无属性填中性词） |
| `{verb}` 动词 | 直取／点向／刺向／抹向（剑·刺击类） | **兵器类型** |
| `{limb}` 部位 | 咽喉／后心／胸口（致命）· 左臂／右腿（非致命） | **致命度门控** + 与动词搭配 |
| `{consequence}` 后果 | 剑锋及体，皮肉焦黑／一股焦臭随之腾起／伤口边缘瞬间烙成黑褐色 | 伤害档 × 剩余生命档 × 系别 |

**片段序列可变长度**：模板自己声明用哪些片段（`segments` 数组），下乘 3 段、绝学 7 段——兑现 `style-guide.md:32`"绝学招式模板可到 3 句的华丽长句"。

**引擎只需"带约束的词库抽取器"**：给定过滤条件，从池中随机取一条。所有门控/搭配/节奏都是数据。

### 4.3 三层门控（缺一不可）

**第一层：致命度门控**（解决穿帮问题）

```
致命部位（咽喉／后心／胸口／头顶）仅当：
    伤害档 ∈ {重, 濒死}  AND  剩余生命档 ∈ {少, 危}
否则只抽非致命部位（四肢／肩臂／腰肋）
剩余生命档 = 危 且伤害档 = 濒死 → 启用「致命一击」专属词库（颓然倒地／气绝身亡）
```

**第二层：搭配约束**（动词 × 部位 × 兵器）

```json
{ "id": "直取", "motion": "thrust", "limbs": ["咽喉", "胸口", "后心", "小腹"] }
{ "id": "扫向", "motion": "sweep", "limbs": ["腰间", "脖颈", "左腿", "右腿"] }
{ "id": "劈落", "motion": "chop",  "limbs": ["头顶", "左肩", "右肩"] }
```

兵器类型决定可用动词池：剑→刺/点/撩/抹/扫/劈，刀→劈/砍/斩/削，棍→扫/砸/抡/戳，拳掌→拍/击/推/按。
抽法：先定兵器 → 定动词池 → 抽动词 → 只在它的 `limbs` 里抽部位。
**引擎做的只是"在一个被过滤的集合里随机"这个通用操作，搭配表是内容不是引擎逻辑。**

**第三层：节奏一致性**

问题：片段各自独立随机会产生"深吸一口气，你**猛地挥出**「白虹贯日」，长剑**缓缓**点向……"这类自相矛盾。
解法：**先定整体节奏档，再按档抽各片段**。每个片段条目带 `tempo`（急／缓／稳），这一击的节奏由招式特性（快招=急）与是否暴击（暴击=急）先定，所有片段只从同档池抽。比"事后检查冲突"简单且保证连贯。

### 4.4 事件流字段（`ADR-0006` 需据此修订）

| 字段 | 状态 | 说明 |
|---|---|---|
| `damage` 伤害数值 | 已有 | — |
| `damageRatio` 伤害占比 | 已有 | 轻/中/重/濒死 四档 |
| `isCrit` / `isDodge` | 已有 | 命中类型 |
| `element` 系别 | **修订自「元素标志」** | 七系 + 无属性（原"元素标志"是悬空字段，Round 5 找到用途：condition 修饰符需匹配它） |
| `source` 作用方式 | **新增** | 内功 / 外功 |
| `moveTier` 招式品阶 | 已有 | 下乘/中乘/上乘/绝学 |
| `attackerRealm` 境界 | 已有 | — |
| `targetHealthTier` | **新增（关键）** | 目标剩余生命档：满/多/半/少/危 五档，离散化 |
| `attackerHealthTier` | **新增** | 攻击者剩余生命档，同五档 |
| `attackerDisplayTier` / `targetDisplayTier` | **新增** | 双方显示档位（50 档）。用于**闪避文本的实力差门控** |
| `beastTrigger` | **新增** | 兽的机制是否在本回合触发，供兽文本插入片段判断 |

**共 5 个新增字段。**

**为什么这些是"现在不定就伤筋动骨"的**：文本选词必须知道"打完还剩多少"，否则会出现"一剑穿喉后敌人继续战斗"的穿帮。`ADR-0006:12` 明写"事件结构后补会伤及存档与模拟器兼容性"。

只靠"伤害占比"做不到：满血的敌人挨了一记占比 30% 的重击，还剩 70%，写"一剑穿喉"就穿帮；濒死的敌人挨同样一记，直接归零，这时才配得上致命描写。

引擎不吐精确数值，只吐档位——符合 `ADR-0006:8`"core 只吐结构化事件"。

### 4.5 闪避文本：独立模板族

现有模板套不上闪避（它有 `{limb}` 和 `{consequence}`，而闪避两者都没有）。**闪避需要自己的一套片段**：

```
{dodgeSubject}{dodgeManner}，{dodgeMove}避过{attacker}的「{move}」{dodgeAftermath}。
```

| 片段 | 说明 | 选择依据 |
|---|---|---|
| `{dodgeSubject}` | 闪避方（**在闪避文本里是主语**） | 即 `{defender}` |
| `{dodgeManner}` | 闪避姿态：气定神闲，笼袖不动／足下生风／仓促侧身／勉强向旁一滚 | **剩余生命档 × 是否有身法 × 实力差** |
| `{dodgeMove}` | 身法招式名（凌波微步、屏翳收风），可为空 | 该角色是否有轻功类武功 |
| `{dodgeAftermath}` | 擦身而过的痕迹："剑锋擦着颈侧掠过，削落一缕鬓发" | **险胜档**专用 |

**「险胜」档性价比最高**：让"闪避成功"有了强弱之分，且**不需要任何新字段**——闪避判定值与阈值的差距本身就是现成数据，内容层按差距分档即可。

**闪避文本受「实力差」门控**（用户原话："总不能大师险胜新手吧。"）：

| 实力关系（双方显示档位之差） | 闪避成功的叙事性质 |
|---|---|
| 攻击方远高于防守方 | **侥幸**——弱者居然躲开了 |
| 双方接近 | **正常**——一来一回 |
| 防守方远高于攻击方 | **从容**——理所当然 |

大师对新手：大师闪避 → 从容档；新手闪避 → 侥幸档。**绝不会出现新手"气定神闲"地躲开大师。**

**随机性保留在档位内部**：逻辑管"该进哪个池"，随机管"池里选哪条"（每档 3-5 条候选）。

注：闪避/招架文本**主语是防方**，但 `{attacker}`/`{defender}` 的语义角色不变（攻击者仍是发起方），只是叙述视角转到防方。

### 4.6 兽文本

**触发条件：兽出场 = 它正在执行它的机制**（解决逻辑性——不是随机乱入）。

**频率节流**：条件满足时按概率出场（config 可调，如 25%）+ 出场冷却（如 3 回合内不重复）→ "不用每招都露脸，但时不时刷存在感"。

**品阶差异 = 片段数，不是频率**（与招式模板的可变长度同一套规则）：

| 品阶 | 片段数 |
|---|---|
| 下乘 | 1 段 |
| 中乘 | 2 段 |
| 绝学 | 3-4 段 |

**与主人的互动：四种类型**

| 类型 | 触发 |
|---|---|
| 救援 | 主人受到致命档伤害 |
| 配合 | 主人出招时同步行动 |
| **反馈** | 主人血量档变化 |
| 增益 | 兽为主人提供加成 |

**"反馈"型最有价值**：与 `{opening}` 的残血词库天然联动——主人残血时 `{opening}` 说"虽已浑身是血，仍作殊死一搏"，兽的反馈紧随其后，两句构成叙事呼应。**用已有字段白捡的戏剧性**。

**架构要求（很轻）**：兽文本是**可选插入片段**，不是主模板一部分。只需要 ① 事件流能标记"这只兽的机制触发了"（`beastTrigger`）；② 文本组合器支持"主模板 + 可选插入"。**都不需要新架构**。

**并发处理**：同一回合可能同时触发"兽出场"和"致命一击"。需要**片段优先级**——**兽片段插在主文本之前**（因果上先发生）。

## 五、兽（驭兽）

### 5.1 定位：本质是装备，不是战斗单位（Round 13 用户提出，推翻助手 NvM 方案）

> 用户原话："兽本身不参与攻击，本质上就是一件装备，区别是这个装备会在文本描述处有一席之地。"

**验证**：逐个检查 7 只兽的效果能否表达为"对主人已有机制的修饰"——**七个全部通过**，且用到的维度恰好就是四个通用参数 `amount / duration / targetSelector / condition`，因为"修饰"的本质就是改这几个维度。

| 兽 | 效果 | 表达为修饰符 | 用哪个维度 |
|---|---|---|---|
| 毒蜂（木） | 扩散中毒 | ✅ | `targetSelector`（单体 → 多个） |
| 火鸦（火） | 引爆灼烧 | ✅ | trigger + `condition`（提前结算 DoT 剩余层） |
| 寒蟾（水） | 延长迟缓 | ✅ | `duration` |
| 铁啄鹰（金） | 维持破防 | ✅ | `duration`（不衰减） |
| 石龟（土） | 转移伤害 | ✅ | `stat-modifier` 减伤 + 叙事包装 |
| 灵隼（风） | 缩短冷却 | ✅ | `rate-modifier` |
| 雷兽（雷） | 暴击追加 | ✅ | `condition: on-crit` + `instant-damage` |

**结论**：① 兽不需独立回合/属性/事件；② 战斗**保持 1v1**；③ 引擎**零新增概念**（它不需要知道"兽"，只知道"带修饰符 + 叙事片段的装备条目"）。

**成本**：从 NvM 模型的 ≈15% 降到 **≈5%**。

**边界（诚实告知）**：兽不能 ① 成为敌人攻击目标；② 有血量、会死；③ 在主人不出招时独立行动。石龟"替你挡下"在装备模型下是**减伤修饰符 + 叙事包装**（实际是伤害减少，叙事上说是石龟挡的），玩家看不出但设计时要知道。

**"参与者集合"抽象仍然要做（≈0 成本）**：现在兽是装备用不上它，但 Round 22 的定时波次已用上（场上 N 个怪物实体）。**不矛盾**——兽=装备是内容决策，参与者集合是形状。

**槽位**：兽走**独立"随从"栏**，不占 6 个装备槽（兵/冠/甲/腕/腰/靴）。理由：兽不是穿戴物，独立栏 UI 清晰，将来升级为单位时栏位模型仍成立。

### 5.2 机制放大器模型（不是伤害复制品）

用户明确要求"不是单纯把七系效果复制到召唤物上"。方案：**兽不造成该系伤害，它改造该系机制的行为方式**。

| 系 | 兽 | 它做的事（放大机制，而非复制伤害） |
|---|---|---|
| 木（疫毒·传染） | 毒蜂／蛊虫 | 把单体中毒**扩散**到邻近目标——把"传染"从概率变成必然 |
| 火（燃爆·灼烧） | 火鸦 | **引爆**灼烧——提前结算目标身上剩余的灼烧层数 |
| 水（滞缓·冰寒） | 寒蟾 | **延长**目标身上的迟缓持续时间 |
| 金（破防·裂伤） | 铁啄鹰 | **维持**破防状态不衰减（本来会随时间恢复） |
| 土（守护·护体） | 石龟 | **转移**伤害——替主角承受一部分，而非自己加外功防御 |
| 风（迅疾·提频） | 灵隼 | **缩短**主角招式冷却，而非自己打得更快 |
| 雷（霆爆·暴击） | 雷兽 | 主角暴击时**追加**一次雷击，而非自己暴击 |

关键：每一个都是"**改变主角已有机制的某个参数**"。兽与七系的关联是机制层面的因果，不是"颜色相同"。构筑深度来自"选哪只兽 = 强化自己主机制的哪个方面"。

### 5.3 形态选择：驭兽，不是召唤

| 形态 | 本体 | 武侠成立吗 |
|---|---|---|
| **驭兽** ✅ | 真实存在的动物，被驯养/驱使 | 小龙女玉蜂、欧阳锋蛇阵 |
| 机关傀儡 | 人造器械，墨家/公输班一脉 | ⚠️ 有先例但边缘，需新势力支撑 |
| 召唤物 | 凭空生成的单位（符箓、撒豆成兵、式神） | ❌ 仙侠谱系，且 `ui-direction.md:9` 已禁符箓 |

**支持证据**：xkx100 有 `clone/animal/` 品类 34 个文件，金庸题材 MUD 把"动物"列为与兵器、衣物并列的大品类；小龙女的玉蜂、欧阳锋的蛇阵是正典。

**反对称据**：`ui-direction.md:9` 白纸黑字禁了符箓；"凭空召唤"在武侠里没有对应物；金庸笔下的青城派是剑派不是符箓派。

机关傀儡作第二条线，留待门派设计时评估。

### 5.4 获取与成长

**门派贡献兑换 + 随境界自动成长**。理由：门派贡献是已有货币（`CONTEXT.md:106`），不需要新系统；随境界自动成长避免第二个养成循环。喂养/进化留 v2。

注意 ADR-0008 明确不做任务体系，故"任务奖励"获取途径排除。

### 5.5 MVP 范围

**2 只兽**：木系毒蜂（进攻型放大器）+ 土系石龟（防御型放大器）。一攻一守，验证"机制放大器"模型。其余五系等模型验证后再补（届时加兽是纯内容，不碰引擎）。

### 5.6 兽的关键能力需要引擎预留

| 需求 | 引擎要什么 | 是不是坑 |
|---|---|---|
| 致命判定 | 伤害管线中"应用伤害之前"的**拦截点**，能判断"这一击会不会致死" | 是形状问题（A.10 第 8 条） |
| 概率触发 | primitive 支持 `chance` 参数 | 不是坑（参数而已） |
| **冷却** | 效果实例要**带 CD 状态**，且这是**运行时数据，要进存档** | **真坑**（A.10 第 9 条） |

➡️ 要预留的是：**效果实例 = { 定义 + 运行时状态（剩余冷却、已触发次数、剩余层数……）}**，运行时状态是存档的一部分。**现在就要进设计，即使 MVP 一只带 CD 的兽都不做。**

## 六、门派

### 6.1 三件套

门派 = **武功池 + 缺省系别 + 生产加成** 三件套（外加贡献货币、脉、师父等）。

### 6.2 脉（`lineageId`）：门派内部的武功池细分

**用户设计**：每个门派内部有不同主张 → 不同武学主张 → 对应七系。担忧：形成 WoW"职业 + 专精"模式。

**这不是 WoW 模式，是武侠正典**：
- **华山派剑宗 / 气宗之争**——《笑傲江湖》整部书的骨架
- **丐帮污衣堂 / 净衣堂**——《射雕英雄传》

两条证明：门派内部有主张分歧是武侠的**原生结构**。WoW 的"专精"也是从这类叙事传统长出来的，源头在武侠这边。

**但"专精"有一个陷阱**：WoW 专精是**互斥**的。若脉也做成"必须选一个、只能学该脉武功"，则硬冲突 `ADR-0001`"流派由玩家玩出来，不预设标签"。

**立场：脉是武功池的细分标签，不是玩家的身份选择。**

| | 脉（采用） | 专精（要避免） |
|---|---|---|
| 它是什么 | 武功池的**归类标签** | 玩家的**身份选择** |
| 能否同时拥有多个 | **能**（受贡献/前置限制） | 不能（互斥） |
| 谁来"选" | 玩家通过**装配**选（招式 4 / 心法 3 槽位限制） | 系统让玩家在进入时选死 |

结果：丐帮既有本系主武功也有某长老的其他系武功，玩家**两个都能学**，但槽位有限 → "专精感"由槽位逼出来，不是系统规定。完全兑现 `ADR-0001`。

**实现很轻**：`content.md:42` 已有 `sectId`，脉只需并行字段 `lineageId`，校验器照 `sectId` 那套做覆盖与连通检查。引擎不认识"脉"——它只是与门派、区域同级的归属标签。

**命名**：武侠里真实存在的有**脉、支、堂、院**。"堂"最贴（污衣堂/净衣堂），"脉"最简洁（剑宗气宗说两脉）。➡️ **统一用「脉」，字段名 `lineageId`**。理由：无术语冲突（"流/流派"＝玩家的战斗构筑，"系"＝七系，"宗"＝门派本身，均已重载）；武侠里"这一脉的武功""剑宗气宗两脉"是自然用法。

### 6.3 门派"要精"：区别落在战斗节奏而非颜色

| 门派 | 缺省系 | 节奏 | 内力特性 |
|---|---|---|---|
| 丐帮 | 火 / 雷 | **爆发型**：短时间倾泻，之后疲软 | 高消耗、高回复需求 |
| 武当 | 水 / 土 | **持久型**：防守反击，拖得住 | 低消耗、续航强 |
| 唐门 | 木 / 金 | **累积型**：毒/破防叠加，越打越疼 | 中等消耗、前置投入长 |

同样"变强"：丐帮感到"一下更疼了"，武当"站得更久了"，唐门"叠得更快了"。比"三个颜色不同的火球"鲜明，且不需额外系统（缺省系别 + 武功池 + 内力参数即可实现）。

### 6.5 五条必须现在留的引擎预留

1. **门派内进阶是运行时进度，进存档**（凡是"玩家身上积累出来的东西"都要在存档设计里预留位置）
2. **已学武功必须与当前门派解耦（最关键）**：`CONTEXT.md:113` 定了 MVP 不可换派偷师，但**数据结构上不能把"已学武功"挂在门派名下**。**正确做法：已学武功是玩家的属性，门派只是它的获取来源**（如同从某校毕业不会因跳槽而失去学位）。这样换派/偷师/叛派惩罚全部退化成"获取权限"问题，而非"剥夺资产"问题。
3. **condition 支持的匹配维度可扩展**（见 11.2）
4. **门派间关系是一张内容表，不是硬编码**：正派/魔教、同盟/敌对将来会变，引擎只做"查关系表"
5. **门派归属是运行时状态、可变更**：存档里应是"当前门派"字段，而非散落各处

**共同点**：这五条都不是"门派系统"，而是"**玩家状态的结构**"。门派的具体内容可以慢慢磨，但"玩家身上存什么"一旦定错，后面全是迁移成本。

### 6.6 入门条件与师父

- **门派入门条件** → **MVP 条件恒真**，但"学习武功"流程需带条件检查点（A.10 第 13 条）
- **师父（`sect.masters`）** → **先只留字段**，无实际内容

## 七、成长与反馈

### 7.1 境界突破时的偏向选择（替代天赋树）

**用户设想**：类似 POE，把一部分人物本身的数值提升写进天赋里。

**用户的观察是对的**：POE 天赋树对流派影响确实不大。POE 有 1300+ 节点，绝大部分是 travel node，玩家社区自己承认"天赋树 80% 是在走过场"。真正决定流派的是**技能宝石链接 + 装备 + 升华**。

**但搬进放置游戏有三个硬冲突**：
1. **节奏来源不存在**：POE 的升级是主动行为，我们的修为是**闭关自动产出**（`CONTEXT.md:13`）。若玩家离线八小时回来发现攒了 20 个未分配天赋点，那不是反馈，是作业。
2. **稀存放置品类的核心承诺**：放置游戏的快感是"我不在也在变强"。若成长切成"自动给一点、手动分配才生效"，就变成"我不在就变慢了"。
3. **重复投资**：流派来源我们已有（装备词缀 × 武功装配 × 兽 × 定向强化），且是 ADR-0001 认可的涌现式。

**但用户真正想要的东西是对的**：本质是**玩家想看到"我这个人变强了"，而不只是"我的装备变强了"**。装备是外物，人物是自身。

➡️ **替代方案：境界突破时的偏向选择**

```
突破至「高手」——选择你的进境方向：
  ○ 外功精进：外功招式伤害 +10%
  ● 内功深厚：内功招式伤害 +10%
  ○ 根基扎实：生命上限 +8%，内力上限 +8%
```

| | 天赋树 | 境界突破选择 |
|---|---|---|
| 新系统 | 需要（点数、UI、重置、平衡） | **不需要**（境界突破界面本来就有） |
| 与进度主轴 | 平行，两套成长 | **就是境界本身**，一套成长 |
| 玩家焦虑 | 1300 节点，新手劝退 | 每次 2-3 个选项，不焦虑 |
| 与放置品类 | 冲突（要手动分配） | **兼容**（突破是里程碑事件） |
| 选择次数 | 100+ | 6 次 |

**关键优势：它天生与内功/外功系统咬合**——"外功精进 vs 内功深厚"用的就是已定的 `source` 维度，不引入任何新概念。若嫌 6 次太少，可每个境界内再分小阶，或把选择扩到七系偏向。**但不要做成树**——树承诺自由，却用最优路径把自由收回去。

### 7.2 变强反馈：四条补法

**诊断**：现有反馈两头重、中间空——

| 频率 | 现有反馈 | 状态 |
|---|---|---|
| 慢（天/周） | 境界突破（6 档）、显示档位（50 档） | 有，但太慢 |
| **中（小时）** | **——** | **空的** |
| 快（分/秒） | 伤害数字、暴击、掉落 | 有 |

玩家 90% 时间活在中高频，那里基本空白。

| 补法 | 内容 | 成本 |
|---|---|---|
| **A. 强度聚合指标** ⏸ | 聚合连续数值，每换装备/每提升境界都会动。与显示档位**互补**：档位给身份感（离散·叙事化），聚合值给进度感（连续·数值化）。**档位之所以显得慢，是因底下没有连续曲线托着它**。**命名待定**（「战力」被用户否决——"成了那些垃圾页游"；「等级」与 `CONTEXT.md:11` Avoid 冲突；「功力」为候选）。若不要聚合数字，A 可整个跳过 | 中 |
| **B. 秘境推进记录** | "已推进至第 18 层（历史最佳 15 层）" | 极低 |
| **C. 战斗内新纪录提示** | "最高伤害 3,847！"存几个 max 值 + 文本。**不叫"战力"，就是具体指标**（最高伤害、最长连击、单次最高中毒层数）。**顺带记录"每一招的最高伤害"**——与 7.3 的定向强化是天然搭档 | 极低 |
| **D. 叙事化反馈** | **战斗文本分档系统本身就是变强反馈机**：同一招弱时"血线缓缓渗出"→ 强了"皮肉焦黑"→ 更强"连人带剑被劈作两段"。**零额外成本**（分档维度已全定） | **零** |

D 条与 `style-guide.md:24` 一致：禁止"数值直出的干瘪句"，所以"造成 100 → 120 点伤害"本就不该是反馈方式，**"伤口从血线变成焦黑"才是**。

**A 的聚合函数本身必须存在**——即使名字没定，离线掉落的 `keepBest` 筛选已需要它（Round 23.7）。

### 7.3 定向强化（涌现式专精）

**用户诉求**：想加入专精里"强化特定技能"的感觉作为奖赏，**但不一定要显式选择专精**。

**既有决策回顾**：`ADR-0005:7` 原文已写"**MVP 不做武器 socket，数据结构预留**"。

➡️ **采用方案 C：词缀定向强化**（`condition: { moveId: "..." }`），**并保留 D（镶嵌/socket）的数据预留**（ADR-0005 已定）。

**为什么 C 正好满足"不显式选择专精"**：玩家从不"选择专精"，他只是反复挑选强化同一招式的装备。挑够三件就成了"专精"，但**系统里从来没有一个叫"专精"的东西**。这是**涌现的专精**而非**声明的专精**，完全兑现 `ADR-0001`。

**顺带解决中频反馈缺失**：每换上一件定向词缀，玩家都能看到那一招变强——这正是小时级的反馈刻度。

**不做天赋树的理由**：成本最高、是声明式的（冲突 ADR-0001）、且与词缀定向强化功能重复。

**熟练度方案额外劝退**：要求跟踪"每个招式用了多少次"（进存档的运行时数据），且**会惩罚玩家换构筑**（换了等于放弃积累），与"鼓励尝试、流派涌现"的初衷相悖。

**引擎要留的唯一一条：`condition` 的维度清单必须可扩展**（见 11.2）。

### 7.4 长期成长 = 数值线 + 构筑线，两条并行

**POE 调研印证**：POE 的**构筑定义主要来自机制改变**（独特装备改变技能行为，如 Facebreaker 让徒手伤害爆增），**数值成长只是让已有构筑更强**。

| 线 | POE | 我们 |
|---|---|---|
| **数值线**（让你能打更高级的内容） | 底材分级 + 词缀阶位 + 品质 + 技能宝石等级 | **底材分层 + 词缀阶位** |
| **构筑线**（让你能用不同方式打） | 技能链接 + 独特装备机制改变 + 升华 | **机制型特色词缀 + 七系主辅组合 + 兽的机制放大器** + 境界突破偏向选择 |

两者相互促进：数值让你能进更高层 → 更高层掉更好的底材与机制词缀 → 新词缀开启新玩法 → 新玩法需要新配装。

**关键**：**POE 的底材就是分层的**——高级区域掉的是**另一个底材**（Rusted Sword → Copper Sword → … → Jewelled Foil），**不存在"一把 Rusty Sword 掉在 Lv80 区域变成极品"这回事**。这印证了 Round 24 的底材分层方案。

## 八、秘境

### 8.1 层内模型 = 定时波次

| | 清完才来下一波 | 到时间就来 |
|---|---|---|
| 本质 | 流程控制 | **压力检验**（清怪速度 vs 生成速度） |
| 难度来源 | 手工调怪物强度 | **自动生成**（两个速度的比值） |
| 玩家感受 | 一段一段的关卡 | 连续的张力曲线 |
| DPS 不足时 | 卡在某一波（硬墙） | **怪物逐渐堆积 → 吃紧 → 崩盘（连续反馈）** |

关键优势：DPS 略低于阈值时，玩家经历"轻松 → 吃紧 → 危险 → 崩盘"的连续曲线，能感知"差一点就撑住了"——这正是放置游戏最想要的"再变强一点就能过"。**比"第 N 层打不过"这种硬墙反馈多得多。**

**触发规则**：

```
触发下一波的条件 = 时间到  OR  上一波已清空     ← 取较早者
```

即"清完才来"与"定时才来"的**并集**。好处：不浪费时间（清完立即来），压力不中断；同时保留了"清不完就堆积"的压力源。

```
进入第 N 层
  ├─ t=0        生成第 1 波
  ├─ t=T1 或 第1波清空（取先到）→ 生成第 2 波
  ├─ ...
  ├─ 第 K 波生成完毕（K = 本层波数）
  └─ 场上清空 且 波次已全部生成 → 通关本层
```

### 8.2 四个参数（全在 `content/config/`，后台可改）

| 参数 | 说明 |
|---|---|
| `waveCount` | 本层几波 |
| `waveInterval` | 波间隔（固定值／区间随机／逐波递减） |
| `waveComposition` | 每波什么怪（固定表／从池随机） |
| `maxConcurrent` | 场上怪物上限 |

**`maxConcurrent` = 技术护栏（12–20），非难度调节**。无上限会导致无限堆积（性能隐患 + 新手一进场就淹没）。超出的波次**延后**而非丢弃。玩法上仍是"堆积→压力"，技术上不失控。

**随机化两层，但可控**：
- 间隔随机：`T ± 20%`
- 构成随机：从本层怪物池抽，但**保底构成固定**（如"每波至少 1 个小兵"）
- 精英/Boss 波**不放进随机池**，固定在指定波次

**核心原则：随机性放在"节奏与搭配"上，不放在"难度"上**——难度必须可预期，否则玩家的变强感知会被运气污染。

### 8.3 层主、解锁、层 modifier

- **层主**：每 N 层一个（如第 5、10 层），非每层都有。理由：每层有 Boss 会让 Boss 贬值且拖节奏；每 N 层给里程碑感，与"秘境推进记录"呼应。
- **秘境解锁**：混合式——前几个链式引导（新手），之后按推荐境界并列开放。符合 `ui-direction.md:44` 的"渐进化解锁 UI"。
- **推荐境界** = **软提示**，非硬门槛；硬门槛只用于"未通关前一层"。
- **层可带 modifier**（如"此层火系伤害 +30%"），与怪物亲和度同族机制，复用同一套。

### 8.4 离线推进

```
单波清怪时间 ≈ 波总HP / 稳态DPS
本层耗时     ≈ Σ清怪 + Σ间隔
离线可推进层数 = 离线时长 / 平均单层耗时
```

推进会在卡住的层停下。

### 8.5 掉落时机与展示

**掉落时机 = 击杀时即时入库**（非探索结束统一结算）。

| 时机 | 行为 | 作用 |
|---|---|---|
| 击杀瞬间 | 浮动提示 | 即时爽感 |
| 探索结算 | 汇总列表，按品阶/稀有度排序 | 不遗漏 + 仪式感 |

**边界**：掉落记录只在**当前探索会话内存活**，会话结束（通关或中断）时展示一次；玩家强退则不展示。**数据已在背包不会丢，只是看不到汇总**——这样不需要为掉落日志增加存档字段。

### 8.6 计时器

### 8.7 MVP 范围

## 九、装备

### 9.1 底材 = 分层（Round 24 修正，取代 itemLevel 方案）

> 用户原话："低等级冒险掉落的装备与高等级冒险掉落的装备，**不光要在数值上区分，更要在文本描述和美术上区分**。"

**修正后的模型**：**每个底材是独立条目，声明自己的层数区间与品阶范围**，高层掉的是**另一个底材**（换名字/描述/美术），而非同一条目加 `itemLevel`。

```
底材条目（每个独立）：
  ├─ 名字 / 描述 / 美术    ← 各自不同
  ├─ 槽位
  ├─ 固有词缀
  ├─ 偏好标签
  ├─ 层数区间（哪个层数段会掉落）
  └─ 品阶范围（能出哪些阶位的词缀）
```

**这与 `ADR-0005:2`"境界提供门槛（解锁秘境/底材）"完全吻合**——是 Round 23 把它过度简化成了 itemLevel，才丢了文本与美术维度。

**美术侧无需改动**：`ADR-0003:8` 的"资产按约定路径引用（`assets/icons/<集合>/<id>.png`）"天然支持每个底材一个 id + 一张图标。

**`itemLevel` 还需要吗** → **MVP 不需要**，降级为**可选乘数**（默认 1.0 = 不启用）。

### 9.2 掉落链 = 七次随机（可配置管线，不能写死）

```
击杀
 ├─ ① 掉不掉（roll）
 ├─ ② 按秘境层数筛选可用的底材池
 ├─ ③ 从池中选一个底材
 ├─ ④ 掷稀有度                    ← 因
 ├─ ⑤ 按稀有度定词缀条数            ← 果
 ├─ ⑥ 抽词缀（受底材偏好标签影响）
 ├─ ⑦ 每条词缀掷阶位（受【底材声明的品阶范围】限制）
 └─ ⑧ 附加底材的固有词缀（固定，非随机）
```

⚠️ **必须是可配置管线**——否则将来想改任一步都要动引擎（A.10 原则三已列为可替换边界）。

**稀有度的因果**（Round 20 用户纠正）：**先定稀有度 → 再按稀有度生成词条**。稀有度是**因**、词条数是**果**，不是由词条数反推。

### 9.3 词缀倾向 = 标签化（非权重表）

**反对权重表**：每个底材列全部 20+ 条词缀权重，新增词缀要回头改所有底材（20 底材 × 60 词缀 = 1200 个数字）。

**标签化**：

```json
// 底材只声明偏好
{ "id": "base-heavy-sword", "preferredTags": ["力量", "破防"] }

// 词缀自己带标签
{ "id": "affix-strength",    "tags": ["力量"] }
{ "id": "affix-armor-break", "tags": ["破防"] }
{ "id": "affix-heavy-hit",   "tags": ["力量", "破防"] }
{ "id": "affix-fire-damage", "tags": ["火系"] }
```

**权重计算**（`权重 = 基础 × (1 + 匹配标签数 × 加成)`，加成 1.0）：

| 词缀 | 标签 | 匹配数 | 重剑掉落时权重 |
|---|---|---|---|
| 力量 +X | 力量 | 1 | 10 × 2 = 20 |
| 破防 +X% | 破防 | 1 | 10 × 2 = 20 |
| 重击 +X% | 力量+破防 | 2 | 10 × 3 = **30** |
| 火系伤害 +X% | 火系 | 0 | 10 × 1 = 10 |

**好处**：新增词缀带 `tags:["力量"]` 即自动被所有偏好"力量"的底材青睐，**零改动**。兑现 `ADR-0008:15`「标签化优先于类型化」。

多标签匹配用**温和叠加**（`基础 × (1 + 匹配数 × 加成)`），非相乘（避免 ×9 失控值）。

### 9.4 特色词缀 = 机制改变型

`ADR-0005:1` 规定绝世（5~6 词缀）含一条特色词缀。➡️ **机制改变型**——不是数值，而是改变机制（如"你的中毒会传染"）。

**额外价值**：这就是**兽的"机制放大器"模型的复用**——同一套 `condition + primitive` 表达，引擎零新增。且让绝世装备的区别是**玩法**而非数值，呼应"流派靠机制涌现"的整体思路。

### 9.5 洗练上限

**MVP：数值只由 tier 决定**。逻辑：低层掉不出 T3，天花板天然受限，不需要额外设上限。

**在底材分层模型下更加成立**：底材条目声明了自己的品阶范围（如玄铁剑只有 T1–T3），所以它的天花板**在数据上就被锁死了**，洗练再多次也出不了 T5。

**保留 `itemLevel` 系数作为乘数配置项**（默认 1.0 = 不生效）。将来若要开启后期数值成长，改一个系数即可，不动结构。

**已知后果**：若数值只由 tier 决定，则第 30 层的 T3 与第 80 层的 T3 一样强，玩家刷齐 T3 满值即**数值毕业**——数值成长有终点，长期追求只能靠换构筑。这正是"数值线 + 构筑线并行"要解决的。

### 9.6 离线掉落 = 玩家可选

配置项 `lootPostProcess: keepBest | allMaterials | lootBox | keepAll` + 参数 N。

| 选项 | 行为 | 适合 |
|---|---|---|
| **keepBest（保留最好的 N 件，其余分解）** | 按评分排序留 N 件 | 默认推荐 |
| allMaterials（全部转为材料） | 离线只产材料 | 背包洁癖、专注洗练 |
| lootBox（打包成战利品箱） | 上线自己开 | 喜欢开箱 |
| keepAll（全部保留） | 不处理 | 硬核（背包会爆） |

**引擎很便宜**：共用"掉落生成 → 后处理"管线，区别只在后处理策略。

**附带**：`keepBest` 需"装备评分"函数——与 7.2A 的"强度聚合指标"是同一件事（计算对象是装备而非角色）。**所以聚合函数必须存在，即使名字没定**。

### 9.7 词缀池形态

**20+ 个词缀条目，每个条目内含 3 阶数值表** → 20+ 个文件而非 60+ 个，且同一词缀的三阶放在一起便于调平衡。这是对 `content.md:30`「每条目一文件」的一个**有意的例外**。

### 9.8 底材规模与两个维度不可混

| 配置 | 算式 | 底材条目数 |
|---|---|---|
| 精简版 | 6 槽位 × 3 层级段 × 1 变体 | 18 |
| **MVP 选定（宽松版）** ✅ | **6 槽位 × 3 层级段 × 2 变体** | **36** |
| 完整版 | 6 槽位 × 5 层级段 × 2 变体 | 60 |
| 完整版（多） | 6 槽位 × 5 层级段 × 3 变体 | 90 |

**因子释义**：
- **槽位**（6）：兵器 / 冠 / 甲 / 腕 / 腰 / 靴
- **层级段**（3）：秘境层数的分段，如 1–5 / 6–15 / 16+
- **每段变体数**（2）：某段某槽位有几种底材可选

**每个条目都要 7 样内容**：名字、描述、`assets/icons/equipment/<id>.png` 图标、固有词缀、偏好标签、层数区间、品阶范围。→ 36 个底材 = **252 项内容**。

⚠️ **两个维度不可混**：
- **秘境层数** → 装备有多强（深度）
- **境界** → 能进哪些秘境、哪些底材入池（gating，广度）；境界还提供裸装基础数值
