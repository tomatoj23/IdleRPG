## 一、Round 1：C3 伤害维度 / C4 槽位语法

### 1.1 提出的问题

- **Q1**：MVP 要不要引入"系别"作为参与运算的第二维度？（推荐 A：不要）
- **Q2**：战斗文本槽位用什么语法？（推荐 `{attacker}` 英文花括号）
- **Q3**：槽位全集取哪几个？（推荐 7 个：attacker/defender/move/weapon/limb/damage/consequence）

### 1.2 关键事实

- `research:211` 证实：xkx 的 `damage_type` 只服务"按 damage_type × 伤害数值双维度**选模板**"，**不参与数值运算**。
- `research:264` 原文建议："IdleRPG 应固化一套更小的槽位协议（如 `{attacker}` `{defender}` `{move}` `{limb}`），combat-text 只存模板，聚合引擎做替换"。
- xkx 槽位体系：`$N/$n` 攻击者/防御者、`$P/$p` 你/他代词、`$w/$W` 兵器、`$l` 被击肢体（人类 21 个部位）。

### 1.3 用户回答

> 全按建议，除了 Q1，因为我没看明白 Q1。**我需要不同类型的伤害**，但命名文本可以中式，如"木火土金水"。

用户提出三点设想：
1. 门派武功（无属性或元素性质）+ 带属性装备 → 产生属性伤害效果（打狗棒法+木系装备 → 中毒）
2. 门派（有元素属性，如丐帮火系）+ 不特定门派但影响武功效果的装备 → 持续伤害，装备提高或引发联动
3. 门派武功有属性 + 装备有属性 → 组合（火系武功 爆裂/燃烧/扩散 + 水系武器 流动/治愈/冰寒 = ？）**用户没想好，要求发散**

### 1.4 本轮结论

- Q1 答案反转为 **B 方向**：伤害带系别维度，且参与运算。
- Q2、Q3 用户未明确反对，后续被 Round 3 的主辅模型吸收。

## 二、Round 2：七系与组合系统

### 2.1 我给出的发散（五行 + 相生相克变异表）

**核心设计选择：相克不要做成"削弱"，要做成"变异"。**
理由：传统"水克火 → 火系伤害 -30%"会让玩家觉得构筑踩雷，是纯负反馈，与 `ADR-0001`"流派由玩家玩出来、不预设标签"相悖——踩雷的构筑没人玩，等于预设了唯一解。

**五行性格**：金=锋锐穿透（破甲、流血）／木=生长蔓延（中毒、缠绕）／水=流动寒（冰寒迟缓、治愈）／火=爆裂燃烧（灼烧、溅射）／土=厚重承载（护体、稳固）。

**相生 5 组**（增强与转化）：木生火=灼烧蔓延／火生土=烬留护体／土生金=攻防一体／金生水=冰寒破甲／水生木=中毒传染。
**相克 5 组**（变异而非削弱）：水克火=蒸汽爆沸（单体转范围+迷雾降命中）／火克金=熔毁（防御归零）／金克木=砍伐（中毒转流血）／木克土=禁锢／土克水=淤泥（减速变定身）。

**属性挂点模型**：
```
招式属性 = 武功自身声明的属性 ?? 继承门派属性 ?? 无
装备属性 = 武器/装备自带的属性，可无
最终效果 = 查组合表
```

### 2.2 用户回答

> 发散的不错，尤其**变异**这里很喜欢，但是：
> **Q4**：是否可加入**风、雷**？这样进一步弱化相克、强化变异、增加组合，需要风雷的机制性格，要与前五系明显区分，**必要时可削减/调整前五系**。
> **Q5**：按推荐。丐帮=火只是举例，先作为缺省。
> **Q6**：参考 Q4，需重新商讨。
> **Q7**：同意建议，但要求：① **不要把内容做进引擎，绝对分离**；② 引擎中的文本描述转为非内容描述（持续伤害、护甲降低、无法攻击，而非"灼烧、中毒、破甲"）；③ **对后台暴露所有可编辑项**（灼烧次数、可否驱除等）；④ 保证未来可添加/移除伤害模式甚至元素属性的扩展空间，**不要过早写死**；⑤ 能否**低耦合模块化**。

### 2.3 我给出的架构方案（回应 Q7）

**两层拆分**：
```
引擎层（core，零题材词汇）
  └─ mechanism primitive 注册表（小、稳定、与题材无关）
内容层（content/）
  ├─ config/elements.json              七系
  ├─ config/element-combinations.json  稀疏组合表
  ├─ config/effect-params.json         primitive 参数 schema
  └─ effects/*.json                    效果 = primitive 组合 + 参数
```

**效果声明式示例**（灼烧）：
```json
{
  "id": "eff-burn",
  "displayName": "灼烧",
  "textKey": "burn",
  "components": [
    { "primitive": "damage-over-time",
      "params": { "ticks": 3, "perTick": 12, "element": "fire", "tickTiming": "turn-start" } },
    { "primitive": "visual-flag", "params": { "flag": "burning" } }
  ],
  "stacking": { "mode": "refresh", "maxStacks": 1 },
  "dispel": { "dispellable": true, "resistance": 0 },
  "expiry": { "mode": "turns", "value": 3, "onDeath": "clear" }
}
```
引擎只读 `components[].primitive` 与 `params`，**永不读 `displayName`**。

**可扩展性的代价表**：

| 未来想做的事 | 需要改什么 | 动引擎吗 |
|---|---|---|
| 加第 8 系 | `elements.json` 加一项 | 否 |
| 删掉一系 | 删一项 + 迁存档 | 否 |
| 加一个新组合 | 组合表加一格 | 否 |
| 加一个新效果（用现有 primitive） | 加 effect JSON | 否 |
| 加一种全新伤害模式 | 注册新 primitive | **是**（只加模块，不改已有代码） |

**代价警告**：① 调试成本（需编辑器与校验器兜底）；② primitive 抽象层若定不稳后期返工（建议参数用通用结构）；③ 组合表结算顺序必须早定（纳入 ADR-0005 的三层管线）。

## 三、Round 3：风雷加入、七系表定稿

### 3.1 关键洞察

五行之所以绕不开"相克"，是因为 5 个元素构成闭环（\(Z_5\)），每个元素必须克一个、被一个克。**加到 7 个，闭环就断了**，没有现成的相生相克表，组合规则必须显式声明——这正好把"相克削弱"赶出去，只留"变异"。

### 3.2 对前五系的削减与调整

- **改动 1：金的「流血」→「裂伤」**。流血/中毒/灼烧三者都是持续伤害，三重重叠。改为"裂伤"（目标受到的所有伤害提高）后，金独占**破防/增伤**轴。
- **改动 2：木的「缠绕」→「传染」**。木（缠绕降频）、水（冰寒降频）、风（疾提频）三系抢同一根"频率"轴。木去掉缠绕，专注**疫毒**轴。频率轴留给水和风，一降一升形成对称。
- **改动 3：土的「稳固」、水的「治愈」、风的「连击/闪」、雷的「震/瞬」留 v2**。

### 3.3 七系表（MVP 形态）

| 系 | 轴 | 机制 | MVP 形态 |
|---|---|---|---|
| 金 | 破防 | 裂伤（受伤加深）、破甲 | 纯数值 modifier |
| 木 | 疫毒 | 中毒（持续伤害）、传染 | **真状态** |
| 水 | 滞缓 | 冰寒（降敌方出手频率）、治愈(v2) | 纯数值 modifier |
| 火 | 燃爆 | 灼烧（持续伤害）、爆裂（溅射） | **真状态** |
| 土 | 守护 | 护体（减伤）、稳固(v2) | 纯数值 modifier |
| 风 | 迅疾 | 疾（提己方出手频率）、连击(v2)、闪(v2) | 纯数值 modifier |
| 雷 | 霆爆 | 暴（暴击率/暴伤）、震(麻痹,v2)、瞬(追加打击,v2) | 纯数值 modifier |

**两系新血的差异化**：风是**己方增益**（提速），与水（敌方降频）对称；雷是**瞬时爆发**（暴击），与火（持续燃烧+范围）对称——火是"烧一阵、烧一片"，雷是"一下很疼"。七根轴：破防／疫毒／滞缓／燃爆／守护／迅疾／霆爆。

**关键**：这张表恰好还是 **2 个真状态 + 5 个纯数值**，与用户已同意的 Q7 折中方案严丝合缝，加两系未增加状态系统负担。

### 3.4 组合模型：主属性决定形态，辅属性决定修饰

用户洞察："水武功+火装备"与"火武功+水装备"产生的效果应该不同——这把组合表从 49 格**对称**矩阵变成**有序**矩阵（同系那 7 格除外）。

> **主属性（来自武功/门派）决定这一招"是什么"**——提供该系的核心效果。
> **辅属性（来自装备）决定这一招"额外怎么样"**——对核心效果施加一个修饰。

| 系 | 主位（核心效果） | 辅位（施加的修饰） |
|---|---|---|
| 金 | 破防（降护甲） | 锐化：加深、转为即时 |
| 木 | 中毒（持续伤害） | 蔓延：扩散、叠加加速 |
| 水 | 冰寒（降频） | 流转：范围化、传导 |
| 火 | 灼烧（持续伤害） | 爆裂：溅射、转为爆发 |
| 土 | 护体（减伤） | 沉滞：延时、固化 |
| 风 | 疾（提频） | 迅发：提速、连击化 |
| 雷 | 暴（暴击） | 震荡：触发式、追加打击 |

**组合示例**（有序）：火主+水辅 = 蒸汽爆沸（灼烧转范围+迷雾降命中）／水主+火辅 = 冰火激变（迟缓持续，结束时冰层骤裂爆发）／木主+风辅 = 毒散（叠层快且传染）／风主+木辅 = 毒风（提速且每次附带少量中毒）／雷主+金辅 = 霆裂（暴击时无视部分护甲）／金主+雷辅 = 锐霆（破甲状态下受击触发追加打击）。

**这解决了"全部相生会不会导致最优解唯一"**：辅属性不是"谁都行，越多越好"，而是七种修饰**方向不同**，取舍来自方向而非强弱。

### 3.5 用户回答

> Q4/Q5/Q6/Q7 详见 Round 2 回答；**同意 primitive 参数用通用结构**（`amount`/`duration`/`targetSelector`/`condition`），但因为七系表还没定，伤害/增益类型可能变化，primitive 最终集合等七系表定完再锁。

## 四、Round 4：护甲、抗性、兵刃伤害

### 4.1 用户提出的新问题

> 金系破甲意味着有护甲属性，但护甲能挡住其他六系吗？还是另需抗性（火抗冰抗）？护甲是干什么用的？只能挡金系？还是再另加一个**兵刃伤害**（没有附加属性的兵刃伤害）？

### 4.2 我的分析

**推荐：护甲 = 唯一通用减伤，不设分系抗性。**
理由：一旦设火抗/冰抗，就要面对七个新属性——七条词缀线、七套装备底材、怪物表七个字段、UI 七个读数，以及 7×7 攻防平衡。而护甲一个属性就能撑起整条防御管线。

**但"兵刃伤害"这一层必须有**：
```
一次攻击的伤害 = 兵刃层（无属性，恒有，受护甲减）
              + 系别层（附加的效果与伤害，可有可无）
```
三个理由：① 用户原始设想里"门派武功无属性"是三种情形之一，没有兵刃层无法表达；② 纯兵刃流应是合法构筑，不该是"什么都没配"的残废状态；③ 让属性成为**附加层**而非**替代层**，换装备不会让既有构筑失效。

**护甲怎么减**：百分比且有递减（`减伤 = 护甲 / (护甲 + K)`），K 与曲线在 config（`ADR-0004:5`）。固定减伤在放置游戏里会随数值膨胀失效，不要用。

**七系在防御侧的分工**：金「破甲」= 降低目标护甲（对**所有**伤害生效，成为团队增伤轴）；土「护体」= 加护甲/减伤；其余五系不碰防御侧。

### 4.3 用户回答

> Q12、Q13 **很难回答**：我确实想要多系伤害的感觉，但多系伤害（抗性）确实会成倍增加工作量，很难抉择。

### 4.4 我的拆解（核心方法）

**指出用户混淆了两件事**：

| 体感来源 | 需要什么 | 成本 |
|---|---|---|
| 不同系的伤害颜色/飘字/文本不同 | 配色表 + combat-text 按系分池 | 几乎免费 |
| 不同系带不同效果 | 效果系统 + primitive | 中等 |
| 打火系怪时火系伤害明显变小 | **怪物侧**一个字段 | 很小 |
| "我这身火抗堆到 75%"的成长感 | **玩家侧** 7 个抗性属性 | 巨大 |

**前三条都不要抗性系统。第四条才是贵的。**

**降本关键 = 把差异放在怪物侧**：
```
monster: { id: "mon-fire-toad", affinities: { fire: -50, water: +30 } }
dungeon: { id: "dun-blaze-cavern", affinities: { fire: -30 } }
```
玩家体感完全一样，但工作量是一个字段 + 一次查表。且**亲和度可按内容量线性铺开**（只给 Boss 和特色怪设，普通怪为 0），抗性系统做不到这点。

**成本对照**：

| 方案 | 玩家侧新属性 | 内容工作量 | 平衡工作量 | 体感 |
|---|---|---|---|---|
| A 单一护甲无亲和 | 0 | 极小 | 极小 | 只有效果差异 |
| **D 单一护甲 + 怪物侧亲和度** | **0** | **一个字段** | **小** | **前三条全有** |
| C 统一异抗 | 1 | 中 | 中 | 弱 |
| B 分系抗性 | 7 | 大 | 大（7×7） | 四条全有 |

**可逆性分析**：
- **不可逆**：只有 Q13 的**伤害构成层数**（兵刃层+系别层 vs 全额转化），它决定伤害计算管线形状，后期改要动存档与全部数值（`ADR-0006:12` 明确警告）。
- **可逆**：玩家侧抗性属性、怪物亲和度、分系词缀线——随时可加。且 `ADR-0004:7` 的精神就是"不要为没做的东西预留 schema"。

**结论**：Q13 的答案必然是 **A2（系别层也给附加伤害）**，否则七系在伤害上完全等价，用户要的感觉就没了。附加伤害 = 兵刃层 × 系别系数（config 里 7 个数），不需要 7 套公式。

## 五、Round 5：双向博弈（玩家也要有抗性）

### 5.1 用户的反驳

> 但是怪物也会有不同系的伤害啊？要不然难度从哪里来呢？所以玩家也得有属性抗性，你觉得呢

### 5.2 我的回应

**承认缺陷**：我上一轮只考虑了"玩家打怪物"一个方向。如果玩家侧只有护甲，怪物用哪一系打都完全等价，**系别在挨打这一侧退化成纯视觉**。用户要的"打火系秘境得换配装"的压力有一半是空的。

**但争一点**："玩家有抗性"和"玩家有 7 个抗性属性"是两件事。**换成"条件修饰符"，大部分成本消失**：

```
词缀「耐火」= stat-modifier {
  target: damage-taken,
  condition: { source: { element: "fire" } },
  amount: -20, unit: "percent"
}
```
走 `ADR-0005` 已有的修饰符聚合管线，只是多一个 `condition` 参数。

| | 属性式抗性 | 条件修饰符式抗性 |
|---|---|---|
| 角色 schema 字段 | 7 个 | **0** |
| 存档新增数据 | 7 个数 | **0** |
| 加第 8 系 | 加字段 + 迁存档 | **加 config 一项** |
| 词缀内容线 | 7 条 | 7 条（**真成本，跑不掉**） |

**ADR-0006 的"元素标志"终于有用了**：伤害事件必须带上自己的系别，否则玩家侧的 condition 修饰符没有东西可匹配。这反过来印证 `ADR-0006:12` 的警告是对的。

**双向博弈的完整形态**：

| 方向 | 进攻方 | 防守方 |
|---|---|---|
| 玩家 → 怪物 | 系别层伤害（兵刃层 × 系别系数） | 怪物**亲和度**（config） |
| 怪物 → 玩家 | 系别层伤害（同理） | 玩家**抗性**（条件修饰符） |

**形式不对称是有意的**：怪物侧用 config（设计者直接指定的关卡参数，不需要成长曲线）；玩家侧用条件修饰符（玩家需要成长与配装，必须是走聚合管线的动态值）。

**代价**：① 7 条词缀线是硬成本；② 抗性需要上限（`-75%`，走乘法区递减）；③ UI 上玩家看不到"火抗 30%"的明确数字，需额外做聚合读数；④ 平衡工作量回来了。

## 六、Round 6：内功/外功二分 + POE 抗性的讨论

### 6.1 用户的新想法

> 把伤害分为**内功伤害**和**外功伤害**，两类都可以有 7 系属性，但防御维度只做**内功防御**和**外功防御**。名称可换成更自然的"护甲（对应外功）"和对应内功防御的一个词，**我没想好**。
> 可是如果不做七系伤害属性和抗性，那**七系的爽感从何而来**呢？
> 另外想起 POE 里各种抗性确实够复杂，但**似乎没有太多影响构筑的多样性，它更多是增加了构筑的门槛，而非变化**，你觉得呢？这一点是讨论，**你可以有自己的观点，只要证据站得住脚，不用非得同意我**。

### 6.2 我的回应

**内功/外功二分：不是替代方案，是正交的**。
- 内功/外功 = 伤害的**作用方式**（打皮肉筋骨 vs 打内腑真气）
- 七系 = 伤害的**性质**（火、毒、寒……）
- 是 2×8 矩阵（8 = 七系 + 无属性），不是二选一。「降龙十八掌」可以是外功·火系，「玄冥神掌」可以是内功·水系。

**它的真正价值**：① 防御从 1 个变 2 个，成本极低（+1 属性），却给怪物设计"外功型 Boss/内功型 Boss"的分类；② 非常武侠；③ 与招式/心法不冲突但也不重复（见 Q21）。

**命名建议**：护甲 / **内力**（最武侠；`CONTEXT.md:42` 招式按冷却自动释放、无内力消耗机制，所以"内力"一词自由）或 护甲 / **气劲**（纯防御语义）。

**术语冲突（后经修正，见 Round 7）**：`CONTEXT.md:47` 心法 Avoid「内功」。

### 6.3 七系的爽感从哪来（正面回答用户追问）

| 来源 | 强度 | 成本 |
|---|---|---|
| **发现搭配**：火+风=蔓延、火+水=蒸汽 | 最强 | 组合表（内容） |
| **视觉/文本**：火焰焦黑、中毒青紫、冰寒结霜 | 很强 | 配色表 + 文本分池，几乎免费 |
| **效果在做不同的事** | 强 | 效果系统，已在方案 |
| **数字手感**：火系一下很大、风系密而小 | 中 | 系别系数，7 个数 |
| **打特定秘境换系明显更轻松** | 中 | 怪物亲和度，一个字段 |
| **我的火抗堆到 75% 了** | **最弱** | **7 个属性 + 7 条词缀线** |

**核心结论：抗性不产生爽感，抗性产生的是"站得住"的资格。** 但压力不能没有——抗性的正确定位是"够用即可"。

### 6.4 POE 抗性：同意用户，并推得更远

**同意，且原因具体**：① 抗性上限固定（默认 75%），所有构筑都堆到同一值 → 不是 decision 是 tax；② 堆满后无进一步空间 → 无深度；③ 不同 Boss 的抗性需求差异不大 → 无切换压力。

**更强的结论**：
> **产生选择压力的从来不是"玩家的防御属性"，而是"怪物身上的系别特征"。**

证据是暗黑 2：同样有抗性上限，但暗黑 2 有**免疫怪**——地狱难度某怪火焰免疫，用火系就是 0 伤害，必须换系。同一个抗性系统，**加了"怪物侧免疫"这个变量，抗性就从门槛变成了选择**。而"怪物对某系免疫/高抗"正是**怪物亲和度**要做的事。

即：**给玩家 7 个抗性属性 → 门槛；给怪物系别亲和度 → 选择。** 同样的体验目标，后者成本是一个 config 字段。

### 6.5 填上漏洞：七系在防御侧 = 效果抵抗

```
减伤层：外功伤害 → 护甲减      内功伤害 → 内功防御减
效果层：火系 → 灼烧            抵抗「抗灼」→ 不被点燃 / 持续时间减半
```
四条理由：① 效果才是七系的灵魂；② 走条件修饰符，复用 ADR-0005，加系不改 schema；③ 比抗性数字更有戏剧性（"我吃了避毒丹" vs "我的毒抗是 60%"）；④ 与内功/外功二分完全兼容。

## 七、Round 7：出招顺序 + 内力系统

### 7.1 用户回答

> **Q19**：还是叫**内功防御 / 外功防御**吧。其他同意推荐。**Q21 怪物也需要内功外功**。
> 新问题 1：玩家招式是自动施展吗？根据 xkx100 调研，每个武功有一系列招式，**这些招式以什么顺序施展**？每次都一样会不会无聊？完全随机会不会没有逻辑？能否让顺序有随机性但**也有逻辑可循**？**七系属性能否影响出招顺序**？或者**影响招式文本描述**？（影响画面效果是前面基本确定的）
> 新问题 2：**武功需要消耗内力**（类似西方游戏魔法值）。所以**七系里的部分效果可以和内力相关**，需要展开讨论。

### 7.2 出招顺序：权重轮盘

**核心**：把出招当成"加权抽签"而非"排序"。
```
每次出手时机 → 在可用招式中按权重随机抽一个
权重 = 基础权重 × 所有命中的调制器
```

| 调制器 | 效果 | 例子 |
|---|---|---|
| 冷却 | 冷却中权重归零 | 已定（`CONTEXT.md:42`） |
| 内力 | 不足则降权/归零 | 见内力节 |
| 重复衰减 | 刚放过 → 临时降权 | 避免三连同一招 |
| 条件加成 | 目标某状态 → 某类升权 | 目标灼烧中 → 火系 ×1.5 |
| **系别亲和** | 装备/武功系 → 同系升权 | 火系装备 → 火招优先 |
| **连携** | 上一招 X → 下一招 Y 升权 | combo 表，内容可配 |

**引擎只有一个通用"加权轮盘"机制**，所有规则是数据，符合 ADR-0004。

**xkx 的"每个武功一系列招式"**：那里其实是**同一招在不同武功等级有不同形态**（`research:88` 的 `query_skill_name(level)`——打狗棒法 lvl 10 是「棒打双犬」，lvl 50 是「天下无狗」）。我们 `CONTEXT.md` 无"武功熟练度"且 Avoid「等级」。
➡️ **建议 MVP 一个招式 = 一个条目，不做多形态**，改用更便宜的方式兑现丰富度：**一个招式配多条文本变体，随机抽**。

**七系影响招式文本**（本轮最推荐的一件事）：
```
招式文本 = 基础模板 + 系别意象词库（填充可选槽位）
```
同一招「白虹贯日」：无属性"剑光如虹"，配火"剑锋赤红，热浪逼人"，配水"剑气凝霜，寒意侵体"。**零引擎成本**，与 `ADR-0006:6` 已要求的"模板与词库分池分级"同一套机制。

### 7.3 内力系统（重大新增）

**放置游戏特有的坑**：自动战斗 + 可离线，玩家不在场时谁管内力？

| 模型 | 战斗中的行为 | 离线结算 | 手感 |
|---|---|---|---|
| **A. 持续回复** | 按秒回内力，边放边回 | **稳态 DPS 公式**（收支平衡点），**O(1)** | 爆发—调息—爆发，最武侠 |
| B. 战斗间回复 | 每场开场满，战斗内不回 | 每场独立 | 开场倾泻后疲软 |
| C. 不回复 | 一条秘境一条内力 | 需模拟整条消耗链 | 压力大，放置感差 |

➡️ **推荐 A**。

**内力耗尽怎么办**：必须定。放置游戏里"没内力 = 打不出招"最挫败。➡️ **零消耗的基础攻击**（拳脚），内力见底自动切换，输出下降但不归零。

**内力上限来源**：境界 + 心法 + 装备词缀，全部走 ADR-0005 管线，引擎不写死公式。

**七系 × 内力映射表**：

| 系 | 内力维度的性格 |
|---|---|
| 金 | 耗内破防：消耗额外内力换取无视部分护甲 |
| 木 | 持续寄赖：中毒需持续供内力维持，或转为**吸内** |
| 水 | 滋养：内力回复加快 / 上限提高 |
| 火 | 倾泻：高消耗换高瞬时爆发，容易见底 |
| 土 | 承载：上限提高 / 受击时内力代偿减伤 |
| 风 | 轻灵：消耗降低 / 出手频率提高 |
| 雷 | 激荡：消耗换暴击；或**内力越低伤害越高**（背水） |

**内力与内功防御要不要挂钩**：武侠直觉诱人，但一旦挂钩，堆内力同时拿到"更多招式 + 更高防御"，易成唯一解。
➡️ **不硬挂钩**，内功防御是独立属性；想要联动就走内容层词缀（"内力上限的 X% 转化为内功防御"）。

## 八、Round 8：闪避（进行中）

### 8.1 已确认的结论

- Q22：出招模型 = 加权轮盘，MVP 先落 4 个调制器（冷却、内力、重复衰减、系别亲和），条件加成与连携表留 v2
- Q23：内力基础模型 = A（持续回复 + 稳态 DPS 离线结算 + 零消耗基础攻击）
- Q24：七系 × 内力映射表可用，**但两处需要"玩家付出代价"**：木系吸内、雷系背水
- Q25：内力**进 MVP，但只进最小形态**（上限 + 消耗 + 持续回复 + 零消耗基础攻击），七系 × 内力差异化留 v2
- Q19：内功防御 / 外功防御
- Q20：七系在防御侧 = 效果抵抗
- Q21：招式可内可外，心法不产伤害，怪物攻击也标内功/外功

### 8.2 结论（用户已接受全部推荐）

- **Q26 = A**：只做闪避，不做招架/格挡。命中判定两级（闪避 → 命中）。理由：`ADR-0006` 与 `style-guide.md:32` 已承诺闪避，不做就是继续留洞；招架虽被 `research:266` 提及，但收益抵不上"多一属性 + 一套文本 + 一层平衡"的成本，留 v2。
- **Q27 = 通用但低基调**：基础闪避 5-10%，上限约 40%，递减曲线 `实际闪避 = 闪避 / (闪避 + K)`（与护甲、抗性同一族公式），K 在 config。理由：放置游戏战斗要快速循环，闪避过高拖节奏；完全为 0 则战斗变纯数字对撞，失去惊险感。
- **Q28 = 不绑定**：闪避是通用数值，风系不独占；风与闪避的关联只体现在**内容层词缀权重**（风系装备更容易出闪避词缀），引擎对此一无所知。

**三条硬约束**：
1. 上限与递减必须有（闪避边际收益非线性：50% 闪避 = 生存时间翻倍，75% = 四倍）。
2. 闪避只让这一次攻击落空，**不跳过回合**（否则高闪避拖成无限战斗，破坏秘境循环节奏）。
3. 闪避是**纯数值**，不是状态 → 不破坏"2 个真状态 + 5 个纯数值"的平衡。

**离线结算**：与内力同构，在线按概率掷、离线用期望值（有效输出 = 原始输出 × (1 − 闪避率)）。用户已为内力接受"稳态 DPS 牺牲精度换 O(1)"，闪避是同一取舍。

**降低闪避**：用已有的 `dodge-modifier` primitive 对**目标**施加负值。土（压）、木（缠）、水（滞）三个系都能表达，语义各不相同。
- 注意：木的「缠绕」已在 Round 3 移至 v2（为把频率轴让给水）。木要承担"减闪避"，走**传染**那条线顺带表达（中毒状态下目标行动受限），或走词缀而非系别效果。**不建议为减闪避把缠绕拉回 MVP**——那会重新引入刚消掉的重叠。
- 用户洞察"降低闪避比提高闪避更有趣"：堆闪避是自己变强，降低闪避是**破解对方构筑**，给 PvE 一个"这 Boss 闪避高，我得带压制手段"的解法维度。

**关键既有事实（重要，勿遗漏）**：
- `ADR-0006:6` 已写"命中类型（**暴击/闪避/反伤**）"——闪避**已经在规划中**。
- `style-guide.md:32` 已写"**暴击 / 闪避 / 反伤 / 中毒** 各有专属模板池"。
- `research:201`：xkx 的判定链是"出招文本 → 判定躲避（**AP vs DP 掷骰**）→【闪避文本】→ 判定招架（AP vs PP）→【招架文本】→ 命中 →【命中附加文本】+【伤害分档文本】+【伤势状态描述】"。

- 七系表里，**风的「闪」被列为 v2**（`风 = 疾（提己方出手频率）、连击(v2)、闪(v2)`）。

## 九、Round 9：代价设计 + 主动释放扩展性 + 槽位修正

### 9.1 木系吸内 / 雷系背水的代价（用户要求"玩家付出一定代价"）

两者都**攻击了内力系统的根基**：吸内让对方失去出招能力，背水让玩家有动机维持空内力——都会让"内力"这个刚建起来的资源失去意义。代价必须补回这个意义。

**木系 · 吸内 —— 四重代价叠加**：

| 代价 | 机制 | 为什么 |
|---|---|---|
| 不能吸干 | 目标内力不会降到上限的 25% 以下 | 保证对方永远还能放低耗招——否则是锁死，不是压制 |
| 转化效率低 | 吸 100 点，自己只进账 40%，其余消散 | 主要价值是削弱对方而非给自己充电，否则变成续航神技 |
| 自身伤害低 | 携带吸内的招式伤害系数 ×0.7 | 用伤害换资源压制，一笔明确的交易 |
| 可被抵抗 | 走 Q20 已定的效果抵抗机制（「固本」类词缀） | 给了克制手段，避免成为必选 |

净效果：吸内是**压制型**路线——打不疼人，但让对方越打越没招。强在节奏破坏，不强在数值。

**雷系 · 背水**（讨论代号，正式命名候选：「背水」「搏命」「破釜」，落文档时定）：

```
触发：内力 < 30% 时开始生效
加成：伤害 ×(1 + 最大加成 × 衰减系数)，最大加成 +50%（config）
```

| 代价 | 机制 |
|---|---|
| 门户大开 | 外功防御同步下降（伤害 +50% 时防御约 −25%） |
| 闪避降低 | 背水时不留余地，闪避率按同比例下降 |
| 需要主动维持 | 内力会自动回复（Q23 持续回复），维持低内力必须持续消耗——不是被动状态，是玩家自己撑住的钢丝 |

净效果：**玻璃大炮**——输出最高、死得最快，且要求配装与招式循环都围绕"把内力花光"设计。有动机成本，不是白拿。

**共同原则**：代价不是"数值打折"，而是"在另一个维度上付账"。保留两个流派的极端手感，只给每个极端配一个真实软肋。全部参数（吸取率、下限阈值、效率、伤害系数、背水阈值、加成上限、防御衰减比）在 config，引擎零写死。

### 9.2 主动释放武功：不在引擎里预先限制

用户要求：先不完全排除主动释放的武功（技能/招式），只是先不做，后续随时可补，**不在引擎里预先限制**，提前考虑扩展性。

**方案：把"谁决定出招"从战斗核心抽出去**

```
战斗循环（core）：
  1. 收集 intent（谁、用什么招、对谁）
  2. 校验（冷却 / 内力 / action-lock 等状态）
  3. 执行 → 产出事件流
  4. 推进时间

intent 来源（可插拔）：
  ├─ auto-source：加权轮盘        ← MVP 唯一
  └─ manual-source：玩家输入队列   ← 未来补，注册即可
```

**core 只认 intent 接口，从不问来源。** 加手动释放的改动清单：① 写一个 `manual-source` 模块注册进去（**core 零改动**）；② UI 加招式按钮（UI 本来就是哑的，`ADR-0004:12`）；③ 招式条目填新字段（数据）；④ 存档记玩家输入/策略配置（由 ADR-0002 版本化迁移兜底）。

**是否现在在 schema 加 `activation` 字段 → 建议不加**，理由是区分两件事：
- **架构维度抽象**——"谁决定出招"是战斗循环必然存在的环节，做成可插拔不是预留，是设计正确。**这个现在就做。**
- **为不确定的功能预留数据字段**——`activation: auto | manual` 是给未设计的功能开字段，会在每个招式条目里躺着直到（也可能永远不）用上，正是 `ADR-0004:7` 反对的预留。

将来真做时，加字段成本由版本化存档迁移（ADR-0002 已定）承担——那是已付过钱的保险。现在加字段 = 为不确定的未来付两次钱。（用户若坚持加亦可，只是要清楚这笔交易。）

### 9.3 战斗文本槽位：重述 + 修正

**已定（Round 1）**：
- 语法 = `{attacker}` 英文花括号，**不是** xkx 的 `$N/$n/$w/$l`
- 删掉 `{动词}`（动词应是模板固定文本，槽位化导致句式雷同，违背 `style-guide.md:46`）
- 删掉 xkx 的代词 `$P/$p`（`style-guide.md:8` 已要求"同一集合内视角一致"，视角是集合级常量）

**修正：全集从 7 个扩到 9 个**（Q26 选了闪避进 MVP，闪避/招架文本以防方为主语，需要防方兵器）：

| 槽位 | 说明 |
|---|---|
| `{attacker}` `{defender}` | 攻方 / 受方 |
| `{move}` | 招式名 |
| `{weapon}` | 攻方兵器 |
| **`{defenderWeapon}`** | **守方兵器（新增，来自 xkx 的 `$W`）** |
| `{limb}` | 被击部位 |
| `{damage}` | 伤害数值 |
| `{consequence}` | 后果文本（从四档词库抽出后嵌套填入） |
| **`{elementFlavor}`** | **系别意象（Round 7 新增）** |

**示例**（一条模板，三种系别）：

模板：`"{attacker}使出一招「{move}」，{elementFlavor}，{weapon}直取{defender}的{limb}，{consequence}。"`

- 火系（`{elementFlavor}`="剑锋赤红，热浪逼人"）：
  > 你使出一招「白虹贯日」，剑锋赤红，热浪逼人，长剑直取黑衣人的咽喉，**剑锋及体，皮肉焦黑，一股焦臭随之腾起**。
- 水系（`{elementFlavor}`="剑气凝霜，寒意侵体"）：
  > 你使出一招「白虹贯日」，剑气凝霜，寒意侵体，长剑直取黑衣人的咽喉，**剑气过处血珠未及渗出便冻成冰粒**。
- 无属性（`{elementFlavor}` 填**中性词，不能用空串**，否则句子出现"，，"）：
  > 你使出一招「白虹贯日」，剑光如练，长剑直取黑衣人的咽喉，**剑锋及体，鲜血溅出**。

**与 xkx 对照**：

| xkx 原文 | 我们的版本 |
|---|---|
| `$N使出一招「棒打双犬」，手中$w化作两道青光砸向$n的$l` | `{attacker}使出一招「{move}」，手中{weapon}化作两道青光砸向{defender}的{limb}` |
| `$n气定神闲……一式「屏翳收风」飘然避过$N这招` | `{defender}气定神闲……一式「{move}」飘然避过{attacker}这招` |
| `手中$W疾点$P右手手腕，迫得$P收招撤回$w` | `手中{defenderWeapon}疾点{attacker}右手手腕，迫得{attacker}收招撤回{weapon}` |

注意第三行：闪避/招架文本**主语是防方**，但 `{attacker}`/`{defender}` 的语义角色不变（攻击者仍是发起方），只是叙述视角转到防方。

## 十、Round 10：文本片段化 + 自伤机制 + 引擎层三个坑

> 用户本轮的方针（重要，指导后续所有讨论）：
> **"不急着砍 MVP，先把想法都聊出来。MVP 自会选择最小方案，就怕后面方案有变更、前面又没想到、反复纠结返工。现在讨论充分是为了避免在引擎层面留下后面没法改没法补的坑。"**

### 10.1 关键发现：事件流缺「目标剩余生命档」

用户原话："总不能剑都戳进咽喉了还能继续战斗。"

这要求的不是"文本写得像样"，而是**文本选词必须知道"打完这一下，对方还剩多少血"**。

`ADR-0006:7` 的事件流字段是"伤害、暴击、元素标志、伤害占比、品阶、境界"——只有"这一击有多重"，**没有"打完还剩多少"**。只靠伤害占比做不到：满血敌人挨占比 30% 的重击还剩 70%，写"一剑穿喉"就穿帮；濒死敌人挨同样一击直接归零，才配得上致命描写。

➡️ **事件流必须补「目标剩余生命档」**（离散五档：满/多/半/少/危，引擎不吐精确数值，符合 `ADR-0006:8`"core 只吐结构化事件"）。

这是"引擎层坑"的活标本：`ADR-0006:12` 自己写着"事件结构必须从第一天就携带呈现所需语境，后补会伤及存档与模拟器兼容性"。

### 10.2 模板片段化：一句话拆成七个可抽词片段

原模板之所以单调，是因为它是"一句固定的话挖了几个洞"。改为**一串片段，每段从词库抽**：

```
{opening}{attacker}{moveIntro}「{move}」，{weaponAction}{elementFlavor}，{weapon}{verb}{defender}的{limb}，{consequence}。
```

| 片段 | 词库示例 | 选择依据 |
|---|---|---|
| `{opening}` 起势 | ""、身形一晃、沉肩坠肘、脚下步法一变、深吸一口气 | 节奏档 |
| `{moveIntro}` 招式引出 | 使出一招／一招／倏然施出／缓缓递出／猛地挥出 | 品阶 + 节奏档 |
| `{weaponAction}` 兵器动作 | ""、剑身剧震、剑光急速穿梭、在半空折返划出一道弧光、剑锋嗡鸣 | 品阶 × 暴击 |
| `{elementFlavor}` 系别意象 | 剑锋赤红，热浪逼人／周身腾起一层赤焰／空气被灼得微微扭曲 | 系别（无属性填中性词） |
| `{verb}` 动词 | 直取／点向／刺向／抹向（剑·刺击类） | **兵器类型** |
| `{limb}` 部位 | 咽喉／后心／胸口（致命）· 左臂／右腿（非致命） | **致命度门控** + 与动词搭配 |
| `{consequence}` 后果 | 剑锋及体，皮肉焦黑／一股焦臭随之腾起／伤口边缘瞬间烙成黑褐色 | 伤害档 × 剩余生命档 × 系别 |

**同一招「白虹贯日」的三种生成结果**：

> **重击·致命档**：身形一晃，你一招「白虹贯日」倏然施出，剑光急速穿梭，周身腾起一层赤焰，长剑点向黑衣人的后心，伤口边缘瞬间烙成黑褐色。
> **中等·火系**：你使出一招「白虹贯日」，剑锋嗡鸣，剑锋赤红，热浪逼人，长剑直取黑衣人的胸口，剑锋及体，皮肉焦黑。
> **轻伤·火系**：沉肩坠肘，你缓缓递出「白虹贯日」，长剑抹向黑衣人的左臂，剑锋掠过，衣袖裂开一道口子，血线缓缓渗出。

最后一句**不可能出现"咽喉"**——伤害档不够，致命部位不在候选池里。

### 10.3 三层门控（缺一不可）

**第一层：致命度门控**（解决穿帮问题）
```
致命部位（咽喉／后心／胸口／头顶）仅当：
    伤害档 ∈ {重, 濒死}  AND  剩余生命档 ∈ {少, 危}
否则只抽非致命部位（四肢／肩臂／腰肋）
剩余生命档 = 危 且伤害档 = 濒死 → 启用「致命一击」专属词库（颓然倒地／气绝身亡）
```

**第二层：搭配约束**（动词 × 部位 × 兵器）
```json
{ "id": "直取", "motion": "thrust", "limbs": ["咽喉", "胸口", "后心", "小腹"] }
{ "id": "扫向", "motion": "sweep", "limbs": ["腰间", "脖颈", "左腿", "右腿"] }
{ "id": "劈落", "motion": "chop",  "limbs": ["头顶", "左肩", "右肩"] }
```
兵器类型决定可用动词池：剑→刺/点/撩/抹/扫/劈，刀→劈/砍/斩/削，棍→扫/砸/抡/戳，拳掌→拍/击/推/按。
抽法：先定兵器 → 定动词池 → 抽动词 → 只在它的 `limbs` 里抽部位。
**引擎做的只是"在一个被过滤的集合里随机"这个通用操作，搭配表是内容不是引擎逻辑。**

**第三层：节奏一致性**
问题：片段各自独立随机会产生"深吸一口气，你**猛地挥出**「白虹贯日」，长剑**缓缓**点向……"这类自相矛盾。
解法：**先定整体节奏档，再按档抽各片段**。每个片段条目带 `tempo`（急／缓／稳），这一击的节奏由招式特性（快招=急）与是否暴击（暴击=急）先定，所有片段只从同档池抽。比"事后检查冲突"简单且保证连贯。

### 10.4 新机制：自伤换增益（七伤拳先例）

武侠里这个机制有现成的根——**崆峒派七伤拳，"伤人七分，自损三分"**（《倚天屠龙记》）；另有天魔解体大法、各种燃血功法。

**代价设计**（按"在另一个维度付账"原则）：

| 代价 | 机制 |
|---|---|
| 无视护甲 | 自伤是精血损耗，不走防御计算——堆防御无法抵消 |
| 无视护体 | 同理，`stat-modifier` 减伤对它无效 |
| 可致死 | 自伤能把自己打死（否则可无脑压血） |
| 触发濒死档 | 自伤后的剩余生命档进入文本选择——你可能把自己写进"颓然倒地"那一档 |

最后一条的双重价值：自伤不只在数值上有代价，**在叙事上也有代价**。

**是否绑定系别：不绑定**。自伤是通用机制，任何系都能有"燃血"词缀。硬塞给火系会重蹈"闪避绑定风系"的覆辙（破坏一系一轴）。

### 10.5 primitive 补 `instant-damage`（重要缺口）

现有 8 个 primitive **没有"立即造成伤害"**。之前未暴露，是因为"攻击造成伤害"被当成战斗默认行为，没被建模成 primitive。

一旦"造成伤害"是个 primitive，自伤就不是特例——它只是 `instant-damage` 的 `target: self`：

| 用法 | target |
|---|---|
| 普通攻击 | 敌方 |
| **自伤（燃血）** | **自身** |
| 反伤 | 攻击者 |
| 溅射 | 相邻目标 |

四个用法共用一套代码；未来加第五种（吸血 = 对敌 instant-damage + 对己 heal）也不用改引擎。

### 10.6 本轮识别出的三个引擎层坑（汇总）

| 坑 | 现在不做的后果 | 现在做的成本 |
|---|---|---|
| **事件流缺「目标剩余生命档」** | 后补要动事件结构 → 伤存档与模拟器兼容性（`ADR-0006:12` 明写） | 加一个离散字段 |
| **缺 `instant-damage` primitive** | 普通攻击/自伤/反伤/溅射四套各写一遍且互相不一致 | 加一个 primitive |
| **文本只是"填空"而非"带约束的多片段组合"** | 将来想要多样性 = 重做整个战斗文本系统 | 抽取器支持过滤条件 |

**共同点：这三个都是"引擎的形状"问题，不是"内容量"问题。内容可以后补，形状不能。**

## 十一、Round 11：宠物/召唤物的调研与立场

### 11.1 调研结果（先查资料再表态，不凭印象）

**支持"动物能进武侠"的证据**：
1. **xkx100 有 `clone/animal/` 品类，34 个文件**（`xkx100-content-structure.md:117`：`clone/` 按品类分目录 weapon(183)/cloth(134)/book(155)/medicine(122)/food(155)/armor(31)/jewelry(19)/**animal(34)**/gift(45)/money/flower/misc）。金庸题材 MUD 把"动物"列为与兵器、衣物并列的大品类——动物在武侠内容模型里有位置。
2. **金庸有"驭兽作战"的硬先例**：小龙女的**玉蜂**（《神雕侠侣》中直接用于攻击）、欧阳锋的**蛇阵**（白驼山）。不是边缘设定，是正典。
3. 随行伙伴亦有先例：杨过的神雕、郭靖的双雕。

**反对"召唤"的证据**：
1. **`ui-direction.md:9` 白纸黑字禁了符箓**："清新淡雅水墨……**武侠而非仙侠**（禁飞剑、金光、**符箓**、云海仙境、渡劫雷电）"。用户举的"道家符箓"这一支，**在我们自己的视觉基准文档里已被明确排除**。
2. **"凭空召唤"在武侠里没有对应物**。撒豆成兵、纸人替身、召雷役鬼属志怪/仙侠谱系，与 `style-guide.md:22` 禁的修仙词（金丹、元婴、灵气、渡劫、飞升）是同一条边界。
3. **青城派**：金庸《笑傲江湖》确有青城派（余沧海、松风观），青城山确是道教名山，但**金庸笔下的青城派是剑派不是符箓派**——没有"青城 = 符箓"的支撑。

### 11.2 立场：同意「驭兽」，反对「召唤」

区别在本体论层面，不是措辞：

| 形态 | 本体 | 武侠成立吗 |
|---|---|---|
| **驭兽** | 真实存在的动物，被驯养/驱使 | ✅ 小龙女玉蜂、欧阳锋蛇阵 |
| **机关傀儡** | 人造器械，墨家/公输班一脉 | ⚠️ 有先例但边缘，需新势力（门派）支撑 |
| **召唤物** | 凭空生成的单位（符箓、撒豆成兵、式神） | ❌ 仙侠谱系，且 `ui-direction.md:9` 已禁符箓 |

**推荐路线：驭兽**。机关傀儡作第二条线留待门派设计时评估。

### 11.3 与七系的「有逻辑关联」：兽是机制放大器，不是伤害复制品

用户明确要求"不是单纯把七系效果复制到召唤物上"。方案：**兽不造成该系伤害，它改造该系机制的行为方式**。

| 系 | 兽 | 它做的事（放大机制，而非复制伤害） |
|---|---|---|
| 木（疫毒·传染） | 毒蜂／蛊虫 | 把单体中毒**扩散**到邻近目标——把"传染"从概率变成必然 |
| 火（燃爆·灼烧） | 火鸦 | **引爆**灼烧——提前结算目标身上剩余的灼烧层数 |
| 水（滞缓·冰寒） | 寒蟾 | **延长**目标身上的迟缓持续时间 |
| 金（破防·裂伤） | 铁啄鹰 | **维持**破甲状态不衰减（本来会随时间恢复） |
| 土（守护·护体） | 石龟 | **转移**伤害——替主角承受一部分，而非自己加护甲 |
| 风（迅疾·提频） | 灵隼 | **缩短**主角招式冷却，而非自己打得更快 |
| 雷（霆爆·暴击） | 雷兽 | 主角暴击时**追加**一次雷击，而非自己暴击 |

关键：每一个都是"**改变主角已有机制的某个参数**"。兽与七系的关联是机制层面的因果，不是"颜色相同"。构筑深度来自"选哪只兽 = 强化自己主机制的哪个方面"。

### 11.4 兽 = 本轮最大的引擎坑

战斗从 **1v1 变成 NvM** 牵动：事件流（谁打谁、参与者身份标记）、权重轮盘（各自轮盘还是统一调度）、内力（兽消耗谁的内力）、闪避/防御（兽是否有自己的属性）、战斗文本（`{attacker}` 可能是"你的灵狐"）、存档、UI、平衡、内容量。

**结论分两半**：① 引擎必须把"战斗参与者"建模成集合而非两个固定角色（成本 ≈ 0，已入 A.10 第 5 条）；② 功能是否进 MVP 是独立决策。

### 11.5 用户决策 + 一次沟通错位（重要，记录以免重犯）

- **Q33 = 接受推荐**：驭兽
- **Q34 = 用户答"兽进 MVP"** —— 但 Q34 原本问的是"**参与者集合抽象现在做不做**"，用户理解成了"兽进不进 MVP"。**助手未指出错位，直接按"兽进 MVP"往下处理**，导致用户困惑："你不是说成本约等于零吗？"
- **Q35 = 同意**：机制放大器模型

**成本对照（澄清后）**：

| 事项 | 成本 |
|---|---|
| "参与者集合"引擎抽象（Q34 本意） | **≈ 0**，且无论兽进不进 MVP 都要做 |
| 兽进 MVP · 2 只 | ≈ 现有 MVP 的 **15%** |
| 兽进 MVP · 7 只 | ≈ 现有 MVP 的 **30-50%** |

**关键点：抽象不随功能走，只随引擎形状走**（内容可以后补，形状不能）。三个选项 A（2 只）/B（不做兽但做抽象）/C（7 只）无论如何都包含那个 ≈0 的抽象。

**后续演进**：Round 13 用户提出"兽 = 装备"，助手验证通过并采纳（A.11），战斗**不再需要** NvM，成本从 15% 降到 5%。**但参与者集合抽象仍保留**——它买的是未来兽升级为真单位的门票。

## 十二、Round 12：闪避文本、兽文本、Q34 重述

### 12.1 Q34 重述（给用户重新决策的机会）

已在上表澄清。用户最终选择：**Q37 = 2 只兽**（见下），即选项 A。

### 12.2 闪避文本：独立模板族（Q38）

现有模板套不上闪避（它有 `{limb}` 和 `{consequence}`，而闪避两者都没有）。**闪避需要自己的一套片段**：

```
{dodgeSubject}{dodgeManner}，{dodgeMove}避过{attacker}的「{move}」{dodgeAftermath}。
```

| 片段 | 说明 | 选择依据 |
|---|---|---|
| `{dodgeSubject}` | 闪避方（**在闪避文本里是主语**） | 即 `{defender}` |
| `{dodgeManner}` | 闪避姿态：气定神闲，笼袖不动／足下生风／仓促侧身／勉强向旁一滚 | **剩余生命档 × 是否有身法 × 实力差** |
| `{dodgeMove}` | 身法招式名（凌波微步、屏翳收风），可为空 | 该角色是否有轻功类武功 |
| `{dodgeAftermath}` | 擦身而过的痕迹："剑锋擦着颈侧掠过，削落一缕鬓发" | **险胜档**专用 |

**三条示例**：
> **从容·有身法**：黑衣人足下生风，一式「凌波微步」飘然避过你的「白虹贯日」。
> **狼狈·残血·无身法**：黑衣人脚步踉跄，勉力向旁一滚，堪堪避开这一剑。
> **险胜**：黑衣人仓促侧身，剑锋擦着颈侧掠过，削落一缕鬓发。

**「险胜」档性价比最高**：让"闪避成功"有了强弱之分，且**不需要任何新字段**——闪避判定值与阈值的差距本身就是现成数据，内容层按差距分档即可。

**兑现既有承诺**：`research:266` 已要求"为「闪避」「格挡」各设基本模板组"，`style-guide.md:32` 已写"暴击/闪避/反伤/中毒 各有专属模板池"——这不是新增需求，是兑现已承诺未兑现的条目。

### 12.3 Q38 补充（用户追加）：闪避文本受「实力差」门控

用户原话："总不能大师险胜新手吧。"

➡️ 闪避文本性质必须反映双方实力关系。落在现成的**显示档位**上（`CONTEXT.md:83` 七档：不堪一击→…→返璞归真，由数值推导）：

| 实力关系（双方显示档位之差） | 闪避成功的叙事性质 | 示例 |
|---|---|---|
| 攻击方远高于防守方 | **侥幸**——弱者居然躲开了 | 你仓促侧身，剑锋擦着颈侧掠过，削落一缕鬓发。这等险象，连你自己都愣了一瞬。 |
| 双方接近 | **正常**——一来一回 | 黑衣人足下生风，一式「凌波微步」飘然避过你的「白虹贯日」。 |
| 防守方远高于攻击方 | **从容**——理所当然 | 黑衣人笼袖不动，只微微一侧身，你这一剑便落了空。 |

**大师对新手**：大师闪避 → 从容档；新手闪避 → 侥幸档。绝不会出现新手"气定神闲"地躲开大师。

**随机性保留在档位内部**：逻辑管"该进哪个池"，随机管"池里选哪条"（每档 3-5 条候选）。

**事件流补充**：**双方显示档位**（离散七档）需与剩余生命档一起进事件流（见 A.9）。

### 12.4 兽文本（Q39）

**触发条件：兽出场 = 它正在执行它的机制**（解决逻辑性——不是随机乱入）

| 兽 | 触发时机 |
|---|---|
| 毒蜂（木） | 目标中毒层数达阈值，毒蜂正在扩散 |
| 火鸦（火） | 灼烧被引爆的那一刻 |
| 寒蟾（水） | 迟缓被延长时 |
| 铁啄鹰（金） | 破甲状态被维持住时 |
| 石龟（土） | 它替主角承受了伤害 |
| 灵隼（风） | 招式冷却被缩短时 |
| 雷兽（雷） | 暴击追加雷击时 |

**频率节流**：条件满足时按概率出场（config 可调，如 25%）+ 出场冷却（如 3 回合内不重复）→ "不用每招都露脸，但时不时刷存在感"。

**品阶差异 = 片段数，不是频率**（与招式模板的可变长度同一套规则）：

| 品阶 | 片段数 | 示例 |
|---|---|---|
| 下乘 | 1 段 | 毒蜂嗡然散开，毒雾漫向一旁。 |
| 中乘 | 2 段 | 你肩头毒蜂骤然振翅，嗡然散开，毒雾顺着剑风向旁边那名敌人漫去。 |
| 绝学 | 3-4 段 | 你肩头那只异种毒蜂清唳般振翅而起，翅上金纹在火光下骤然一亮——它绕着黑衣人的伤口盘旋半匝，尾针连点，将那处青紫的毒气生生逼向了旁边同伴的脉络。 |

**与主人的互动：四种类型**

| 类型 | 触发 | 示例 |
|---|---|---|
| 救援 | 主人受到致命档伤害 | 石龟横过身来，替你硬受了这一记——壳上裂开一道细纹。 |
| 配合 | 主人出招时同步行动 | 你一剑递出，灵隼自肩头掠下，双爪抓向对方双目。 |
| **反馈** | 主人血量档变化 | 灵隼低鸣盘旋，似在催促你退开。 |
| 增益 | 兽为主人提供加成 | 石龟昂首，一层土黄色的光晕自你周身浮起。 |

**"反馈"型最有价值**：与 `{opening}` 的残血词库天然联动——主人残血时 `{opening}` 说"虽已浑身是血，仍作殊死一搏"，兽的反馈紧随其后，两句构成叙事呼应。用已有字段白捡的戏剧性。

**架构要求（很轻）**：兽文本是**可选插入片段**，不是主模板一部分。只需要 ① 事件流能标记"这只兽的机制触发了"；② 文本组合器支持"主模板 + 可选插入"。**都不需要新架构**。

**并发处理**：同一回合可能同时触发"兽出场"和"致命一击"（如石龟替你挡下致命伤）。需要**片段优先级**——建议**兽片段插在主文本之前**（因果上先发生）。

## 十三、Round 13：兽的引擎预留 + 门派山头 + 变强反馈

### 13.1 用户确认：兽 = 装备（采纳，推翻助手原方案）

用户原话："兽本身不参与攻击，本质上就是一件装备，区别是这个装备会在文本描述处有一席之地。"

**助手验证结果：用户是对的。** 逐个检查 7 只兽的效果能否表达为"对主人已有机制的修饰"：

| 兽 | 效果 | 能否表达为修饰符 | 用哪个维度 |
|---|---|---|---|
| 毒蜂（木） | 扩散中毒 | ✅ | `targetSelector`（单体 → 多个） |
| 火鸦（火） | 引爆灼烧 | ✅ | trigger + `condition`（提前结算 DoT 剩余层） |
| 寒蟾（水） | 延长迟缓 | ✅ | `duration` |
| 铁啄鹰（金） | 维持破甲 | ✅ | `duration`（不衰减） |
| 石龟（土） | 转移伤害 | ✅ | `stat-modifier` 减伤 + 叙事包装 |
| 灵隼（风） | 缩短冷却 | ✅ | `rate-modifier` |
| 雷兽（雷） | 暴击追加 | ✅ | `condition: on-crit` + `instant-damage` |

**七个全部通过**，且用到的维度恰好就是 Round 3 定的四个通用参数 `amount / duration / targetSelector / condition`——因为"修饰"的本质就是改这几个维度。

**证据链**：① 七效果全可表达为修饰符 → 兽不需独立回合/属性/事件；② 战斗**保持 1v1**，不需 NvM；③ 引擎**零新增概念**（它不需要知道"兽"，只知道"带修饰符 + 叙事片段的装备条目"）；④ 直接兑现 `ADR-0004`。

**未想到的额外收益：这个能力可推广。** "装备可以提供叙事片段"是通用能力，于是兵器 → `{weaponAction}`、兽 → 兽片段、名剑「流云剑」→ "剑身发出一声清鸣"，**三者是同一类东西**。兽不需要任何专属文本机制，只复用"装备声明 narrative 片段"这个能力。

**成本重估**：

| | 助手原估（NvM 模型） | 装备模型 |
|---|---|---|
| 战斗模型 | NvM（需参与者集合） | **1v1（不变）** |
| 兽的属性/血量/AI/成为目标 | 需要 | **不需要** |
| 新增工作量 | ≈15% | **≈5%** |

**边界（诚实告知）**：兽不能 ① 成为敌人攻击目标；② 有血量、会死；③ 在主人不出招时独立行动。石龟"替你挡下"在装备模型下是**减伤修饰符 + 叙事包装**（实际是伤害减少，叙事上说是石龟挡的），玩家看不出但设计时要知道。

**"参与者集合"抽象仍然要做（≈0 成本）**：现在兽是装备用不上它，但将来兽升级成真单位（能被打、能死、能独立行动）时不用重写战斗系统。**不矛盾**——兽=装备是内容决策，参与者集合是形状。

**槽位**：兽走**独立"随从"栏**，不占 6 个装备槽（兵/冠/甲/腕/腰/靴）。理由：兽不是穿戴物，独立栏 UI 清晰，将来升级为单位时栏位模型仍成立。

### 13.2 兽的关键能力（挡濒死）需要引擎预留

用户追问：关键能力需概率 / CD 限制，是否要在引擎层面完善或预留？

| 需求 | 引擎要什么 | 是不是坑 |
|---|---|---|
| 致命判定 | 伤害管线中"应用伤害之前"的**拦截点**，能判断"这一击会不会致死" | 是形状问题，现在定便宜 |
| 概率触发 | primitive 支持 `chance` 参数 | 不是坑（参数而已） |
| **冷却** | 效果实例要**带 CD 状态**，且这是**运行时数据，要进存档** | **真坑** |

➡️ 要预留的是：**效果实例 = { 定义 + 运行时状态（剩余冷却、已触发次数、剩余层数……）}**，运行时状态是存档的一部分。**现在就要进设计，即使 MVP 一只带 CD 的兽都不做。**

**更深的坑：概率触发在离线结算时怎么办？**
闪避可用期望值（影响 DPS，连续）；但**致命保护是 0/1 事件**，决定角色死不死，期望值会失真（不能说"平均死了 30%"）。三个解法：

- **A. 离线战斗不致死**：离线秘境推进不会让角色死亡，最多"推不动了"；致命保护离线时不参与计算。
- **B. 保守模型**：离线假设保护未触发，若致死则判定推进失败。安全但偏严。
- **C. 离线按 CD 就绪与否确定性判断**：不掷骰，CD 好了就算触发。可预测但在线/离线规则不一致。

➡️ **推荐 A**：放置游戏的离线结算本就该是"稳的"，让死亡成为离线结果会让玩家不敢离线，与放置品类核心体验冲突；在线时该机制照常掷骰，严肃性未丢。

### 13.3 activation 字段

**解释**（用户追问该字段是什么）：招式的**释放方式**——`auto`（按冷却 + 权重轮盘，当前唯一形态）／`manual`（玩家点按钮）。

**决策**：现在不加（避免为不确定功能预留数据字段），但**引擎层 intent 源可插拔现在就做**；将来加字段的成本由 ADR-0002 版本化存档迁移兜底。**不锁死后期扩展**（用户明确要求）。

### 13.4 代价数值后置

用户："代价数值也随便选，重要的是先把机制写好，或者不限制未来调整机制的空间。"

**保证**：所有代价参数在 config，调整数值不改引擎；**连机制本身也能扩展**（新的代价形式 = 新的 primitive 组合或新的 condition）。现在写下的任何数字都不是承诺，只是初值。

### 13.5 门派内部「山头/派系」：同意做分化，反对做成互斥专精

**用户设计**：每个门派内部有不同"山头"（长老主张不同）→ 不同武学主张 → 对应七系（如丐帮是火系，但某性情温和的长老传下木系/水系武功）。担忧：形成 WoW"职业 + 专精"模式。

**这不是 WoW 模式，是武侠正典**（证据）：
- **华山派剑宗 / 气宗之争**——《笑傲江湖》整部书的骨架。同门之内，一派主"以剑招为先"，一派主"以气御剑"，斗到你死我活。
- **丐帮污衣堂 / 净衣堂**——《射雕英雄传》。同一帮派，一派破衣烂衫守旧制，一派衣冠齐整求变通。

两条证明：门派内部有主张分歧是武侠的**原生结构**，不是从 WoW 借来的。WoW 的"专精"也是从这类叙事传统长出来的，源头在武侠这边。

**但"专精"有一个陷阱**：WoW 专精是**互斥**的。若山头也做成"必须选一个、只能学该山头武功"，则硬冲突 `ADR-0001`"**流派由玩家玩出来，不预设标签**"。

**立场：山头是武功池的细分标签，不是玩家的身份选择。**

| | 山头（建议） | 专精（要避免） |
|---|---|---|
| 它是什么 | 武功池的**归类标签** | 玩家的**身份选择** |
| 能否同时拥有多个 | **能**（受贡献/前置限制） | 不能（互斥） |
| 谁来"选" | 玩家通过**装配**选（招式 4 / 心法 3 槽位限制） | 系统让玩家在进入时选死 |

结果：丐帮既有火系「降龙十八掌」也有某长老的木系/水系武功，玩家**两个都能学**，但槽位有限 → "专精感"由槽位逼出来，不是系统规定。完全兑现 `ADR-0001`。

**实现很轻**：`content.md:42` 已有 `sectId`，山头只需并行字段 `factionId`，校验器照 `sectId` 那套做覆盖与连通检查。引擎不认识"山头"——它只是与门派、区域同级的归属标签。

**命名**（用户说"长老只是举例"）：武侠里真实存在的有**脉、支、堂、院**。"堂"最贴（污衣堂/净衣堂），"脉"最简洁（剑宗气宗说两脉）。建议按门派气质选。

### 13.6 门派"要精"：区别落在战斗节奏而非颜色

3 个门派要鲜明区别，建议用**节奏差异**而非系别差异：

| 门派 | 缺省系 | 节奏 | 内力特性 |
|---|---|---|---|
| 丐帮 | 火 / 雷 | **爆发型**：短时间倾泻，之后疲软 | 高消耗、高回复需求 |
| 武当 | 水 / 土 | **持久型**：防守反击，拖得住 | 低消耗、续航强 |
| 唐门 | 木 / 金 | **累积型**：毒/破甲叠加，越打越疼 | 中等消耗、前置投入长 |

同样"变强"：丐帮感到"一下更疼了"，武当"站得更久了"，唐门"叠得更快了"。比"三个颜色不同的火球"鲜明，且不需额外系统（缺省系别 + 武功池 + 内力参数即可实现）。

### 13.7 变强反馈：档位缺一个「中频刻度」

用户问题："档位变化其实是比较慢的，但是玩家需要提升时的反馈，有没有其他办法增加变强的反馈？"

**诊断**：现有反馈两头重、中间空——

| 频率 | 现有反馈 | 状态 |
|---|---|---|
| 慢（天/周） | 境界突破（6 档）、显示档位（7 档） | 有，但太慢 |
| **中（小时）** | **——** | **空的** |
| 快（分/秒） | 伤害数字、暴击、掉落 | 有 |

玩家 90% 时间活在中高频，那里基本空白。四个补法（按性价比排序）：

**A. 战力 / DPS 指标（最该做）**
由全部属性聚合的连续数值，每换装备/每提升境界都会动，把慢反馈转为连续反馈。与显示档位**互补而非重复**：显示档位 = 离散的、叙事化的（"炉火纯青"）给身份感；战力 = 连续的、数值化的（12,345 → 12,890）给进度感。**档位之所以显得慢，正是因为它底下没有一条连续曲线托着它**。顺带补一个旧账：审计发现"战力"在 `CONTEXT.md` 零出现（`ui-direction.md:189` 用过一次），需正式词条。

**B. 秘境推进记录**
"已推进至第 18 层（历史最佳 15 层）"。秘境分层是已有设计（`CONTEXT.md:53`），加最高层记录几乎零成本，给玩家每次刷新都能看到的里程碑。

**C. 战斗内「新纪录」提示**
"最高伤害 3,847！"存几个 max 值 + 文本提示，换高频惊喜感。

**D. 叙事化的变强反馈（免费，最贴我们的设计）**
**战斗文本分档系统本身就是一台变强反馈机。** 同一招打同一敌人：弱时"剑锋掠过，衣袖裂开一道口子，血线缓缓渗出"→ 强了"剑锋及体，皮肉焦黑，一股焦臭随之腾起"→ 更强"一剑斩落，黑衣人连人带剑被劈作两段"。**文本自己会告诉玩家"你变强了"**，且是最有体感的方式。伤害档、剩余生命档、系别、品阶这些分档维度已全定，这条反馈**现成、零额外成本**。且 `style-guide.md:24` 已要求避免"数值直出的干瘪句"——所以"造成 100 点伤害 → 120 点伤害"本就不该是我们的反馈方式，**"伤口从血线变成焦黑"才是**。

## 十四、Round 14：专精式强化、术语换词、门派机制全景

### 14.1 "强化特定技能"：有必要，但不做成专精系统

用户诉求：想加入专精里"强化特定技能"的感觉作为奖赏，**但不一定要显式选择专精**。

**既有决策回顾**：`ADR-0005:7` 原文已写"**MVP 不做武器 socket，数据结构预留**"——这个需求 ADR 早有预见，只是当时未命名。

**四种实现路径对比**：

| 方案 | 怎么做 | 成本 | 与已有设计的关系 |
|---|---|---|---|
| **C. 词缀定向强化** | 装备词缀带 `condition: { moveId: "mrt-gb-003" }` | **极低** | 完全复用修饰符 + condition |
| A. 熟练度（用得越多越强） | 跟踪使用次数 | 中 | 需新系统 + 存档字段 |
| D. 镶嵌 / socket | 武器打孔镶嵌 | 中 | ADR-0005 已声明预留 |
| B. 天赋树 / 专精点 | 新资源 + 新 UI + 平衡 | 高 | 全新系统 |

➡️ **推荐 C，并保留 D 的数据预留（ADR-0005 已定）**。

**为什么 C 正好满足"不显式选择专精"**：玩家从不"选择专精"，他只是反复挑选强化「降龙十八掌」的装备。挑够三件就成了"降龙专精"，但**系统里从来没有一个叫"专精"的东西**。这是**涌现的专精**而非**声明的专精**，完全兑现 `ADR-0001`"流派由玩家玩出来，不预设标签"。

**顺带解决中频反馈缺失**：每换上一件定向词缀，玩家都能看到那一招变强——这正是小时级的反馈刻度。

**不做独立系统的理由**：B（天赋树）成本最高、是声明式的（冲突 ADR-0001）、且与词缀定向强化功能重复。

**A（熟练度）额外劝退**：要求跟踪"每个招式用了多少次"（进存档的运行时数据），且**会惩罚玩家换构筑**（换了等于放弃积累），与"鼓励尝试、流派涌现"的初衷相悖。

**引擎要留的唯一一条：`condition` 的维度清单必须可扩展**。至少要有：
```
element（系别）/ source（内功|外功）/ moveId（招式）/ moveTier（品阶）
targetState（目标状态）/ sectId（门派）/ lineageId（脉）/ equippedTag（装备标签）
```
只要 condition 可扩展，"强化特定技能"永远不用改引擎——将来想加"强化某门派的全部武功""强化所有绝学"，都只是加一个匹配维度。

### 14.2 术语换词：「山头」→「脉」（lineage）

用户明确要求："山头"只是举例，有歧义，别写进文档。

**候选词冲突排查**：

| 候选 | 冲突 |
|---|---|
| 流 / 流派 | ❌ `CONTEXT.md:32` 流派 = 玩家的战斗构筑，重载 |
| 系 | ❌ 已用于七系（火系/水系），重载 |
| 宗 | ⚠️ 华山剑宗气宗确实用"宗"，但"宗"在武侠里也指门派本身，易混 |
| **脉** | ✅ 无冲突 |

➡️ 确定用 **「脉」，字段名 `lineageId`**。理由：无术语冲突；武侠里"这一脉的武功""剑宗气宗两脉"是自然用法；`lineage` 准确表达"传承支系"。
（丐帮"污衣堂/净衣堂"是内容层具体命名，字段统一用 `lineageId`。）

### 14.3 变强反馈：「战力」太土，改用「功力」或跳过

用户否决"战力"（"成了那些垃圾页游"），说"还不如等级"。

**但「等级」用不了**：`CONTEXT.md:11` 明写 `境界` 的 `_Avoid_: 等级、Level、阶段`——等级会和境界（进度主轴）抢同一语义位置。

**替代词：「功力」**
- 武侠里"功力深厚""此等功力"是自然用法
- 不与任何已有术语冲突（修为 = 境界经验值；内力 = 战斗资源；造诣 = 显示档位的描述）
- 不土

**若连聚合数字都不想要，A 可整个跳过**，B+C+D 足够撑起中频反馈：
- **B. 秘境推进记录**："已至第 18 层（历史最佳 15）"——零成本
- **C. 新纪录提示**："最高伤害 3,847！"——零成本，且**不叫战力，就是具体指标**（最高伤害、最长连击、单次最高中毒层数）
- **D. 叙事化反馈**：免费，最武侠

**保留建议**：C 里顺带记录"**每一招的最高伤害**"——它与 14.1 的"强化特定技能"是天然搭档：专精了某招，就能看到那一招的纪录不断被自己刷新。

### 14.4 门派机制全景（穷举）+ 五条引擎预留

用户要求：内容可以随意，**关键是机制**；现在要尽可能想到所有能加进来的机制，先做好设计或留好坑，留足扩展。

| # | 机制 | 引擎需求 | 现在要留吗 |
|---|---|---|---|

| 5 | 门派内进阶（贡献等级） | **运行时进度，进存档** | **是** |
| 6 | 师父（`sect.masters`） | NPC 数据，无战斗 | 否 |
| 7 | 脉（武功池细分） | 无（归属标签 `lineageId`） | 否 |
| 8 | 入门条件 | condition 维度 | 否（归入 condition 可扩展） |
| 9 | **换派 / 偷师**（MVP 不做） | **已学武功须与当前门派解耦** | **是（关键）** |

**五条必须现在留的**：

1. **门派内进阶是运行时进度，进存档**（与 A.10 第 9 条同类——凡是"玩家身上积累出来的东西"都要在存档设计里预留位置）
2. **已学武功必须与当前门派解耦（最关键）**：`CONTEXT.md:113` 定了 MVP 不可换派偷师，但**数据结构上不能把"已学武功"挂在门派名下**。**正确做法：已学武功是玩家的属性，门派只是它的获取来源**（如同从某校毕业不会因跳槽而失去学位）。这样换派/偷师/叛派惩罚全部退化成"获取权限"问题，而非"剥夺资产"问题。

4. **门派间关系是一张内容表，不是硬编码**：正派/魔教、同盟/敌对将来会变，引擎只做"查关系表"

**共同点**：这五条都不是"门派系统"，而是"**玩家状态的结构**"。门派的具体内容（几个门派、叫什么、什么武功、什么脉）可以慢慢磨，但"玩家身上存什么"一旦定错，后面全是迁移成本。

### 14.5 遗留待查（落文档时处理）

`CONTEXT.md:11` `境界` 的 Avoid 列表含「等级」，但本会话已出现"门派贡献等级""秘境层数""武功熟练度"等用"等级"语义的地方。落文档时需检查：**是否要给 Avoid 加限定说明**（如 Avoid「等级」仅针对"角色进度"语义，不针对其他层级语义），或改用更精确的词（品阶 / 层 / 阶 / 造诣）。

## 十五、Round 15：天赋系统评估 + 战斗/武学/装备维度穷举

> 用户本轮要求：门派穷举保留，但**更需要战斗场景、武学（内/外功）、装备等维度上各种情况的穷举**——目的是把引擎的坑照出来。

### 15.1 天赋系统：不建议建，但用户真正想要的东西值得要

**用户设想**：类似 POE，把一部分人物本身的数值提升写进天赋里，但对流派影响不大；问能否用天赋系统强化升级过程的反馈。

**用户的观察是对的**：POE 天赋树对流派影响确实不大。POE 有 1300+ 节点，绝大部分是 travel node（+10 力量这类过路点），玩家社区自己承认"天赋树 80% 是在走过场"。真正决定流派的是**技能宝石链接 + 装备 + 升华**。所以天赋树的本质是**把"人物自身数值成长"显性化的容器**，价值不在构筑深度（那是错觉），而在让玩家每升一级都"得到一点什么"。

**但搬进放置游戏有三个硬冲突**：

1. **节奏来源不存在**：POE 的升级是主动行为（得刷怪才有经验），所以"升一级得一点"与玩家行动节奏天然咬合。我们的修为是**闭关自动产出**（`CONTEXT.md:13`），玩家不主动刷。若玩家离线八小时回来发现攒了 20 个未分配天赋点，那不是反馈，是作业。
2. **稀存放置品类的核心承诺**：放置游戏的快感是"我不在也在变强"。若成长切成"自动给一点、手动分配才生效"，就变成"我不在就变慢了"。
3. **重复投资**：流派来源我们已有（装备词缀 × 武功装配 × 兽 × 定向强化），且是 ADR-0001 认可的涌现式。天赋树不是流派来源（POE 已证明），却要吃掉一整套 UI + 平衡 + 存档成本。

**但用户真正想要的东西是对的**："把人物本身的数值提升写进去"的本质需求是——**玩家想看到"我这个人变强了"，而不只是"我的装备变强了"**。装备是外物，人物是自身。这是真实的心理需求，放置游戏普遍做得不好。

➡️ **替代方案：境界突破时的偏向选择**

```
突破至「三流」——选择你的进境方向：
  ○ 外功精进：外功招式伤害 +10%
  ● 内功深厚：内功招式伤害 +10%
  ○ 根基扎实：生命上限 +8%，内力上限 +8%
```

| | 天赋树 | 境界突破选择 |
|---|---|---|
| 新系统 | 需要（点数、UI、重置、平衡） | **不需要**（境界突破界面本来就有） |
| 与进度主轴 | 平行，两套成长 | **就是境界本身**，一套成长 |
| 玩家焦虑 | 1300 节点，新手劝退 | 每次 2-3 个选项，不焦虑 |
| 与放置品类 | 冲突（要手动分配） | **兼容**（突破是里程碑事件，不是高频操作） |
| 选择次数 | 100+ | 6 次（6 个境界） |

**关键优势：它天生与内功/外功系统咬合**——"外功精进 vs 内功深厚"用的就是已定的 `source` 维度，不引入任何新概念。若嫌 6 次太少，可每个境界内再分小阶，或把选择扩到七系偏向。**但不要做成树**——树承诺自由，却用最优路径把自由收回去。

### 15.2 换词与搁置

- ✅ 「山头」→ **「脉」（`lineageId`）** 确认
- ⏸ 「战力 / 等级 / 功力」之争**搁置**，等用户有想法再定

### 15.3 战斗形态穷举（先抛一个必须澄清的矛盾）

| 形态 | 我们的设计现状 |
|---|---|
| 1v1 | 战斗文本是 `{attacker}` vs `{defender}` 两方，暗示 1v1 |
| **1vN / NvM** | **`ADR-0005` 火系「爆裂（溅射）」暗示多目标**——1v1 下溅射毫无意义 |
| 连续战斗（车轮战，不回血） | 秘境"通关一层解锁下一层"，层内是否连续未定 |
| 限时 / 生存战 | 未涉及 |
| Boss 战（特殊机制） | 未涉及 |
| PvP / 门派切磋 | 未涉及 |

⚠️ **必须现在定的矛盾**：若秘境战斗是 1v1，「溅射」就是死机制；若是 1vN，战斗文本、目标选择、兽的"扩散"都要重新设计。
➡️ **建议支持多目标**，因为溅射、扩散中毒、范围伤害都需要它，且它们**已经写进设计了**。1v1 只是"单体"的一个特例。

**引擎需求**：`targetSelector` 必须支持 **单体 / 全体 / 相邻 / 随机 N 个 / 除主目标外**。

### 15.4 武学穷举：招式可能造成的效果

| # | 效果 | 现有 primitive 能表达吗 |
|---|---|---|
| 1 | 造成伤害 | ✅ `instant-damage` |
| 2 | 持续伤害 | ✅ `damage-over-time` |
| 3 | 增益 / 减益 | ✅ `stat-modifier` |
| 4 | 控制 | ✅ `action-lock` |
| 5 | 破甲 | ✅ `armor-modifier` |
| 6 | 闪避修正 | ✅ `dodge-modifier` |
| 7 | 频率修正 | ✅ `rate-modifier` |
| 8 | 暴击修正 | ✅ `crit-modifier` |
| 9 | **治疗 / 回复** | ❌ **缺 `heal` primitive** |
| 10 | 吸血 / 吸内 | ❌ 需 `instant-damage` + `heal` 组合 |
| 11 | 反伤 | ✅ `instant-damage`（target=攻击者） |
| 12 | 溅射 | ✅ `instant-damage`（targetSelector=相邻） |
| 13 | 连击（多次打击） | ⚠️ 需"重复执行"能力，待确认 |
| 14 | 驱散（移除状态） | ❌ **缺 `dispel` primitive** |
| 15 | 护盾 | ⚠️ 可归入 `stat-modifier`，但护盾有"吸收量"语义，可能需独立 |

⚠️ **发现两个 primitive 缺口：`heal` 和 `dispel`**。好消息：它们与 `instant-damage` 同族（都是"对某目标施加一次效果"），加进来不破坏结构。但**现在不加，将来加这两类效果就要动引擎**。

**心法可能提供的效果**：常驻数值加成 / 条件加成（当 X 时 +Y）/ 被动触发（当暴击时…）/ **改变机制行为**（如"灼烧不再衰减"——与兽的放大器模型同构）。

| 2 | 系别加成（火系伤害 +X%） | ✅ 已有 |

### 15.6 伤害计算管线——引擎的真正核心（关键）

**`ADR-0005:6` 定的"固定值 → 加法百分比 → 乘法区"是修饰符的聚合规则，不是伤害的应用顺序**——这两件事必须分开定义，否则将来"破甲和火系加成谁先算"会变成糊涂账。

**建议的管线阶段**（每阶段都可被 modifier 命中，顺序固定）：

```
1.  基础值      base          招式/装备/境界的原始数值
2.  固定加成    +flat         "火系伤害 +50"
3.  百分比加成  +add%         "火系伤害 +15%"（同类相加）
4.  乘法加成    ×mult         "所有伤害 ×1.2"（异类相乘）
5.  暴击        crit          暴击率判定 + 暴伤倍数
6.  攻方修正    source        内功/外功各自走对应防御
7.  守方减免    defense       护甲 / 内功防御（百分比递减）
8.  易伤/抗性   vuln/res      目标受伤加深、系别亲和度
9.  闪避判定    dodge         0 或 1
10. 最终值      final
11. 后续触发    post          反伤、吸血、溅射、兽的追加
12. 应用        apply         扣血 → 判定致死 → 触发致命保护
```

**第 12 步含上一轮说的「应用前拦截点」**（致命保护在此插手）。

⚠️ **这一条必须现在定死**：① 它是所有数值平衡的地基；② 每个 modifier 都要声明自己作用于哪个阶段；③ **后改会让所有已配数值失效**。

### 15.7 时间、随机、存档

**时间模型**：招式按"冷却"自动释放 → 战斗是**实时推进（tick）**，非回合制。所有冷却、DoT 跳数、状态持续都挂在 tick 上。离线结算 = tick 快进 + 稳态公式。

**随机性来源（穷举）**：出招权重、暴击、闪避、词缀 roll、掉落、文本选择、兽出场、致命保护。
→ **每一处都要回答"离线时怎么办"**。统一策略是"在线掷骰、离线期望值"，但**致命保护是例外**（0/1 事件，期望值失真），已单列待决。

**存档应该装什么（穷举，最容易漏的一块）**：

| 类别 | 内容 |
|---|---|
| 角色 | 境界、修为、生命、内力（当前/上限）、门派、门派贡献、门派等级 |
| 装备 | 6 槽 + 随从栏（兽）、每件装备的词缀与 roll 值 |
| 武学 | 已学（**与门派解耦**）、已装配（招式 4 / 心法 3）、每招的使用/纪录数据 |
| 状态 | buff/debuff 实例（**含剩余冷却、剩余层数、剩余时长**） |
| 进度 | 秘境每层最高记录、生产活动等级、各项纪录（最高伤害等） |
| 资源 | 药材、材料、丹药、货币 |
| 随机 | 若采用种子随机，需存种子状态 |

### 15.8 本轮新发现的坑

| # | 坑 | 建议 |
|---|---|---|
| 1 | **1v1 vs 多目标未定**（溅射暗示多目标） | 现在定：支持多目标，1v1 是特例 |
| 2 | **primitive 缺 `heal`、`dispel`** | 现在补（与 instant-damage 同族，不破坏结构） |
| 3 | **伤害管线阶段未定义** | 现在定死（见 15.6），后改伤所有数值 |

### 16.2 术语质疑：「境界」是不是仙侠的？

**用户原话**："武侠里有'境界'这种东西吗？这不是仙侠的吗？"

**查证结论：质疑基本成立，但错的是"境界"这个词，不是那套序列名。**

**"境界"在武侠 vs 修真的用法差异**：

| | 用法 | 例子 |
|---|---|---|
| **武侠** | 对**造诣程度**的描述性词汇，**不是等级体系** | 古龙"手中无剑、心中有剑"是一种境界；金庸更多用"造诣""火候""功力" |
| **修真/仙侠** | **等级体系本身的名称** | 炼气→筑基→金丹→元婴→化神；"突破境界"是修真标配短语 |

**问题不在词源，在当代玩家认知**：读过修真小说的人看到"境界突破"第一反应就是仙侠。且与 `style-guide.md:22` 已禁的修仙语汇线（金丹期、元婴、灵气、渡劫、飞升）同源——**"境界"是漏网之鱼**。

**但序列名本身是纯正江湖语汇，必须保住**：
- "一流高手""二流高手""三流货色""不入流"——武侠评价武功高低的常用词
- "绝顶高手"（金庸常用）、"一代宗师"（武侠核心概念）
- 修真绝不会用"三流""不入流"命名境界（它们用"炼气三层"）
- **这套序列是我们最武侠的资产之一**

**结论：换统称，保留序列。**

### 16.3 换词候选与推荐

| 候选 | 武侠用法 | 问题 |
|---|---|---|
| **造诣** ✅ | "武功造诣""颇有造诣"——武侠正宗，指"达到的程度"，正好是进度主轴 | 与 `CONTEXT.md:83` 显示档位的"造诣描述"撞名，需把后者改掉 |
| 火候 | "火候未到""火候已足"——武侠常用 | 偏指技艺熟练度，做进度主轴略窄 |
| 功力 | "功力深厚" | 更像"当前强度"不像"层级"；且 Round 14 推荐它做战力/强度指标 |
| 品流 / 流品 | 与序列前四档（不入流/三流/二流/一流）高度契合 | 后两档"绝顶/宗师"不配套 |
| 保留境界 | 武侠里确有其词 | 玩家认知已被修真占据 |

➡️ **推荐把「境界」改为「造诣」**，同时把 `CONTEXT.md:83` 的显示档位"数值→**造诣**描述"改叫 **「火候」**。

改完的语义分工：

| 术语 | 是什么 | 序列 |
|---|---|---|
| **造诣**（原"境界"） | 你在江湖上的层次，进度主轴 | 不入流 → 三流 → 二流 → 一流 → 绝顶 → 宗师 |
| **火候**（原"造诣描述"） | 你当前实战的强弱，由数值推导 | 不堪一击 → 初窥门径 → 稍有所成 → 登堂入室 → 炉火纯青 → 出神入化 → 返璞归真 |

一个是你**练到了哪一层**，一个是你**现在打得怎么样**——本就该分开命名。

### 16.4 连带问题：「突破」要不要一起换？

`CONTEXT.md:22` 的"突破"（Avoid: 升级）同样有嫌疑——"突破境界"是修真标配短语。武侠里更常说"武功大进""更上一层楼""功力精进"。

### 17.3 「修为」是不是修仙词：中等嫌疑，建议保留

- **本义**：佛道用语，指"修行的功夫"。武侠用，仙侠也用，**仙侠用得远多**。
- **嫌疑排序**：`境界`（修真体系核心词，重）> `突破`（修真标配短语，重）> **`修为`（两边都用，中）**
- `style-guide.md:22` 禁用表未列它。

➡️ **建议保留**：它是**经验值，主要出现在 UI 数字与进度条上，很少进叙事文本**；而"境界""突破"是天天出现在玩家眼前的等级名与升级动作，所以那两个更该换。

### 17.4 用户硬性要求：引擎不写死（**比术语重要得多**）

**用户原话**："引擎层面别写死名称和江湖序列数量就行（可以写有几层，但是别不能改，或者改了数量就崩了）"

**翻译成四条技术约束**：

| # | 约束 | 为什么 |
|---|---|---|
| 1 | 江湖序列定义为 `content/config/` 里的**数组**，引擎只遍历 | 增删一档不改代码 |
| 2 | 引擎代码**不出现序列长度字面量**（不能有 `for i in 0..6`） | 否则改数量就崩 |
| 3 | **引擎与存档只存数字等级，武侠词是 UI 层的映射**（⚠️ **Round 18 用户纠正，推翻 Round 17 的 id 化方案**） | 见下方展开 |
| 4 | 数值→档位的映射是**配置表**（`displayTiers`），不是硬编码阈值 | 否则改档数要改代码 |

**第 3 条展开（用户 Round 18 纠正，这是本轮最重要的一条）**：

> 用户原话："引擎里就直接写成等级，我只是要你在 UI 上显示武侠风，这样它只是一个映射关系，明白吗！我在外面删不删档位，跟你等级一毛钱关系没有，只是要修改映射关系。"

**正确的分层**：

| 层 | 存什么 | 例子 |
|---|---|---|
| **引擎 core** | 数字等级 | `realmLevel: 3`、`skillLevel: 147` |
| **存档** | 数字等级 | 同上 |
| **UI / 内容映射表** | 武侠词 | `3 → "高手"`、`147 → "炉火纯青"` |

于是：
- **改名称**（高手 → 好手）：只改映射表，**引擎与存档都不动**
- **删一档 / 加一档**：只改映射表，**引擎与存档都不动**
- **改档位划分**（哪些数值区间对应哪一档）：只改映射表

**⚠️ 助手 Round 17 的错误**：当时建议"存档存 `rankId` 而非索引"，理由是"删档位会让存档错位"。这是**过度设计**——用户指出删档位改的是映射关系，与等级数值无关，所以数字等级天然免疫。本条已按用户方案改写。

**唯一需要迁移的例外**：**改变等级上限**（如境界从 6 级减到 4 级）。此时 `level: 5`、`level: 6` 的存档会越界，需要一条迁移规则把它们收敛到新上限。这不是"改映射"，是"改量程"，属于 `ADR-0002` 版本化迁移的范畴。

**注意区分两条原则**（不要混淆）：
- **内容条目**（武功、装备、怪物、兽）：`content.md:30` 的"**id 一经发布不可变更**"**继续有效**——它们有语义、有交叉引用，必须 id 化
- **等级 / 档位序列**：**用数字 + 映射表**，不需要 id（用户方案）

**同样适用于**（凡"有顺序的数值序列"，都是数字 + UI 映射）：
江湖序列 6 级／显示档位（Round 18 改为 **50 档**）／词缀阶位 T1–T3／伤害占比 4 档／剩余生命 5 档／秘境层数。

**不适用**（仍需 id 化 + 枚举在 config）：七系、武功品阶、脉、门派、primitive 类型、事件/命中类型。

> ⚠️ **Round 19 修正**：本条原把「装备稀有度」也列入"需 id 化"，**已更正**——稀有度的规则（词缀条数 0/1-2/3-4/5-6）在表里，可数值化为 0–3 + 映射表（见 A.17）。**真正的标准不是"有没有语义"，而是"引擎是否按具体值分支"**（见 Round 19.4）。

## 十九、Round 19：xkx100 档位机制调研 + 数值化穷举 + 枚举增删

### 19.1 xkx100 到底有没有"等级"？（用户提问，调研结论）

**用户的印象**："他似乎没有等级这种东西？好像是内力越强越厉害？"

**事实：印象一半对一半错。**

| 印象 | 事实 |
|---|---|
| "没有等级" | ✅ **人物等级确实没有**——xkx100 不像网游有 Lv.1→Lv.60 的人物等级 |
| | ❌ **但武功有等级**——技能等级是**无上限整数**（实战常见 0~300+，基本武功被引擎限制到 300，`combatd.c` L371/434/608） |
| "内力越强越厉害" | ⚠️ **因果反了**——内力不是独立成长线，而是**派生资源** |

**xkx100 的档位机制（出处 `xkx100-kungfu-combat.md:175`）**：

> 技能等级是无上限整数……**显示时按等级除以固定步长映射为 50 档中文品阶**（`cmds/skill/skills.c` L10-21）

即：**数值（等级）→ 显示映射（50 档词）**。⚠️ **这正是用户 Round 18 提出的方案，xkx100 早就这么做了。**

**内力的真实定位（出处 `:192`、`:86`、`:87`）**：

- `内力保有上限 = 基本内功级别 × 15`，激发特殊内功后 `= 内功有效级别 × 10`（`doc/help/neigong` L30-36）
- **内力上限是由"内功等级 × 系数"派生出来的**，不是独立攒出来的
- 用途：① **消耗品**——练功每次扣 qi 30-50 与 neili 10-50（`anran-zhang.c` L110-121）；② **学习门槛**——`max_neili < 1500` 不能学某武功（`valid_learn`）；③ 招式前置条件（内力 > 200）

所以因果是：**内功等级高 → 内力上限高 → 能学更强的武功、发更猛的招**。内力是中间变量，不是根源。

**人物的强弱由什么决定**（出处 `xkx100-content-structure.md:81`）：
`combat_exp`（战力数值，100~100 万）+ 四维（str/int/con/dex）+ 气血/内力上限 + 各门武功等级。**没有单一的人物等级。**

**招式解锁也是等级驱动**（`:88`、`:183`）：
- `query_skill_name(level)` 按当前等级返回应显示的招式名（**向下取最大解锁档**）
- 黯然销魂掌 17 招的解锁点（各项 `lvl`）：`0, 10, 20, 30, 40, 60, 70, 80, 100, 110, 120, 140, 150, 160, 170, 180, 200` ——**高档间距拉大**

**对我们的三点启示**：
1. ✅ **印证了用户的映射方案**：xkx100 = 数值（武功等级）+ 显示映射（50 档）+ 等级门槛（招式解锁）。我们要的架构它已经是了。
2. ⚠️ **我们的"内力"设计与 xkx100 同构且更简**：我们定的是"内力上限 = 境界 + 心法 + 装备词缀"（Round 7），xkx100 是"内功等级 × 15"。都是**派生资源 + 消耗品**，方向一致，不必改。
3. 💡 **"招式按等级解锁"这个机制我们没做**（Round 15.4 第 13 项"连击"、Round 7 的"招式多形态"都留了 v2）。xkx100 的解锁点设计（`0,10,20,...,200`，高档间距拉大）是个可抄的曲线模板。

### 19.2 「超凡入圣」「天人合一」豁免（用户决定）

#### C. 映射表结构（支持"1–5 级对应一个档位"）


- **区间映射**（`min`/`max` → 词），天然支持多对一（1–5 级 → 一档）

- 增删档位 = 改这张表，**引擎与存档零改动**
- 校验器需检查：区间无缝、无重叠、覆盖全值域

### 19.4 真正标准：不是"有没有语义"，而是**引擎是否按具体值分支**

**用户追问**："有语义的枚举也是可以后期增删而不动引擎的吧？"

**答：可以，但有严格前提——引擎绝不按枚举的具体值分支。**

| | 引擎行为 | 后果 |
|---|---|---|
| ❌ 反例 | `if (element === "fire") { ... }` | 加第 8 系要改代码 |
| ✅ 正例 | `apply(config.elements[elementId].modifiers)` | 加第 8 系只加 config 一项 |

**把分支条件数据化，是让枚举可增删的关键**。例：内功/外功要走不同防御——不要写成 `if (source === "internal") 走内功防御`，而是：

```json
{ "id": "external", "defenseStat": "armor" }
{ "id": "internal", "defenseStat": "innerDefense" }
```
引擎读 `defenseStat` 字段，**不按 id 分支**。于是加第三种作用方式（如"暗器"）只需加一条 config。

**加 vs 删的不对称性**：

| 操作 | 安全性 | 需要做什么 |
|---|---|---|
| **加成员** | ✅ 安全 | 加 config 项即可（新成员不被旧内容引用） |
| **删成员** | ⚠️ 需谨慎 | ① 校验器检查是否有内容条目引用它；② 处理已有引用（内容条目 + 存档）→ `ADR-0002` 版本化迁移 |

**结论**：只要遵守"引擎不按具体值分支"，**有语义的枚举也能后期增删不动引擎**。删除的成本不在引擎，在**引用完整性**（这与 `content.md:30` 的"id 一经发布不可变更"是同一件事——该条约束的是"改名"，而"增删"由校验器 + 迁移兜底）。

**必须 id 化的三类**（引擎或内容会硬引用）：
1. **primitive 类型**（`instant-damage`/`heal`/`action-lock`…）——引擎按 id 找实现
2. **内容条目**（武功、装备、怪物、兽、门派、脉）——`content.md:30`
3. **事件类型 / 命中类型**（命中/暴击/闪避/反伤）——引擎按 id 分支（闪避 = 0 伤害）

## 二十、Round 20：稀有度因果修正 + 映射表结构扩展 + 显示档位映射定案

### 20.1 稀有度的因果关系被我写反了（用户纠正）

**用户原话**："稀有度这里因果关系反了，因为后面生成装备的时候，需要先定这个装备是什么稀有度，然后才是根据稀有度随机生成词条或固定生成词条。"

**我错在哪**：A.17 把稀有度写成"整数 0–3 + 映射：寻常/精良/罕见/绝世 + **词缀条数规则**（0/1-2/3-4/5-6）"——这个写法把"词缀条数"摆成了与 label 并列的映射结果，**暗示稀有度是由词条数反推的**。

**正确的因果链**（装备生成流程）：

```
1. 先定底材（base type）
2. 再定稀有度（roll 或固定）        ← 稀有度是【独立主属性】
3. 按稀有度查出词条数规则 → 生成对应条数的词条（随机或固定）
4. 每条词条的阶位（T1–T3）由掉落等级 / 秘境层数决定
```

即：**稀有度是原因，词条数是结果**。稀有度在前，词条在后——这与 `ADR-0005:1` 的"底材 × 稀有度 × 词缀阶位"结构一致，我在 A.17 的表述违反了它。

### 20.2 映射表项 = 配置对象，不只是一个 label（由 20.1 推广）

既然稀有度这类映射项要**携带下游规则**，那么映射表的每一项就不该只是一个字符串，而是一个**配置对象**：

```json
{
  "rarity": [
    { "level": 0, "label": "寻常", "affixCount": { "min": 0, "max": 0 }, "hasSpecialAffix": false },
    { "level": 1, "label": "精良", "affixCount": { "min": 1, "max": 2 }, "hasSpecialAffix": false },
    { "level": 2, "label": "罕见", "affixCount": { "min": 3, "max": 4 }, "hasSpecialAffix": false },
    { "level": 3, "label": "绝世", "affixCount": { "min": 5, "max": 6 }, "hasSpecialAffix": true }
  ]
}
```

**推广到所有映射表**：
- 显示档位 50 档 → 每项可携带配色、飘字大小、屏震强度等呈现参数
- 境界等级 → 每项可携带解锁内容列表（秘境、底材、武功）
- 门派等级 → 每项可携带可兑换清单
- 生产活动等级 → 每项可携带产出速率与可进入区域

**原则**：**映射表的 key 是数值，value 是一个配置对象**——名称只是这个对象的一个字段，规则、解锁、呈现参数都在同一处。引擎读对象里的字段，永远不读 label 做判断。

**校验器新增检查项**：映射表各项的下游规则必须自洽（如稀有度 level 递增时 `affixCount.min` 不得递减）。

### 20.3 显示档位映射方式 = A（数值区间表）

用户确认采用 **A. 数值区间表**（`displayTiers`），而非照搬 xkx 的"等级 ÷ 步长"。

理由（与 Round 19.3 一致）：我们的数值是连续增长的战斗数值，不是 0–300 的离散技能等级；区间表可随时调整疏密（前期密、后期疏，或反之），而"÷ 步长"的疏密是固定的。

结构：`[{ min, max, label, ...呈现参数 }]`，支持多对一（1–5 级 → 一档），校验器检查无缝/无重叠/全覆盖。

## 二十二、Round 22：#3 秘境结构（二）——定时波次深化 + 手动目标选择

### 22.1 定时波次的价值：难度是涌现的，不是配出来的

| | 清完才来下一波 | 到时间就来 |
|---|---|---|
| 本质 | 流程控制 | **压力检验**（清怪速度 vs 生成速度） |
| 难度来源 | 手工调怪物强度 | **自动生成**（两个速度的比值） |
| 玩家感受 | 一段一段的关卡 | 连续的张力曲线 |
| DPS 不足时 | 卡在某一波（硬墙） | **怪物逐渐堆积 → 吃紧 → 崩盘（连续反馈）** |

关键优势：DPS 略低于阈值时，玩家经历"轻松 → 吃紧 → 危险 → 崩盘"的连续曲线，能感知"差一点就撑住了"——这正是放置游戏最想要的"再变强一点就能过"。**比"第 N 层打不过"这种硬墙反馈多得多。**

### 22.2 模型（含用户 Round 22 追加的提前规则）

**用户追加**："如果这波打完了但没到时间，则提前来。"

```
触发下一波的条件 = 时间到  OR  上一波已清空     ← 取较早者
```

即"清完才来"与"定时才来"的**并集**。好处：不浪费时间（清完立即来），压力不中断；同时保留了"清不完就堆积"的压力源。

```
进入第 N 层
  ├─ t=0        生成第 1 波
  ├─ t=T1 或 第1波清空（取先到）→ 生成第 2 波
  ├─ ...
  ├─ 第 K 波生成完毕（K = 本层波数）
  └─ 场上清空 且 波次已全部生成 → 通关本层
```

**四个参数**（全部进 `content/config/`，后台可改）：

| 参数 | 说明 |
|---|---|
| `waveCount` | 本层几波 |
| `waveInterval` | 波间隔（固定值／区间随机／逐波递减） |
| `waveComposition` | 每波什么怪（固定表／从池随机） |
| `maxConcurrent` | 场上怪物上限 |

### 22.3 三个定案细节

**1. 场上怪物上限 = 技术护栏，不是难度调节**
无上限会导致无限堆积（性能隐患 + 新手一进场就淹没）。建议设 12–20 的**技术性上限**，超出的波次**延后**而非丢弃。玩法上仍是"堆积→压力"，技术上不失控。

**2. 随机化两层，但可控**
- 间隔随机：`T ± 20%`（保留节奏感，不至于变运气）
- 构成随机：从本层怪物池抽，但**保底构成固定**（如"每波至少 1 个小兵"）
- 精英/Boss 波**不放进随机池**，固定在指定波次

**核心原则：随机性放在"节奏与搭配"上，不放在"难度"上**——难度必须可预期，否则玩家的变强感知会被运气污染。

**3. 这用上了为兽预留、一度看似白做的抽象**
Round 11 定的"**战斗参与者建模为集合**"（A.10 第 5 条），后因兽按装备模型实现而一度无用武之地。**现在定时波次用上了**——场上同时存在 N 个怪物实体，各有血条、状态、目标选择。
→ 值得记住的教训：**形状抽象的成本是零，但价值要等某个功能出现时才兑现**。当时保留它是对的。

### 22.4 手动目标选择（用户提出，Q48 同理）

**用户原话**："建议加上手动选择，因为**如果一个技能的属性是随机单体目标，但本层需要先秒掉某个关键怪，怎么办**？"

这是一个真实的战术需求：**随机单体 + 需要先杀关键怪 = 玩家失控**。

➡️ 解法落在 Round 13 已定的 **intent 模型**上，而且发现 intent 的三个维度可以**独立配置来源**：

```
intent = {
  actor:   谁释放    ← auto
  skill:   用什么招  ← auto（权重轮盘）| manual（玩家点招式）
  target:  对谁      ← auto（targetSelector）| manual（玩家点目标）
}
```

于是三种形态自然浮现，不需要新增机制：

| 形态 | skill | target | 说明 |
|---|---|---|---|
| 纯自动 | auto | auto | 当前默认 |
| **半自动**（用户要的） | **auto** | **manual** | 系统出招，玩家指定打谁 |
| 全自动 | manual | manual | 玩家点招式 + 点目标 |

**重要**：这说明 Round 13 的"intent 源可插拔"不只支持"手动放招"，还支持"手动选目标"——**因为三个维度可独立配置**。这是对 Round 13 抽象的一次正向验证。

**⚠️ 由此引出一个必须解决的矛盾**：**离线时没有玩家输入**，target 只能走 auto。若某层需要先集火关键怪，离线就推不过去。

➡️ **推荐解法：玩家配置"目标优先级策略"**（如"优先精英"／"优先残血"／"优先最高威胁"）。离线时按此策略选目标，玩家的战术意图被保留，离线推进不受影响。这是**策略配置**而非实时操作，符合放置品类。

**引擎要求**：`targetSelector` 需支持两类来源——① 招式自带（内容声明）；② 玩家策略配置（存档）；③ 实时玩家点击（仅在线）。三者优先级：③ > ② > ①。

### 22.5 用户确认（Q49–Q51 按推荐）

- **Q49 = 波间隔与构成的随机化**：间隔 `T ± 20%`；构成本层池随机 + 保底固定；精英/Boss 不进随机池

```json
  "preferredTags": ["力量", "破甲"],
  "itemLevelRange": { "min": 10, "max": 100 }
}
```

同一把剑在不同层的表现：

| 掉落位置 | itemLevel | 可出阶位 | 数值系数 |
|---|---|---|---|
| 第 3 层 | 3 | T1 | ×1.0 |
| 第 30 层 | 30 | T1–T2 | ×1.6 |
| 第 80 层 | 80 | T1–T3 | ×2.8 |

**三方案对比**：
- A（无等级）：第 3 层与第 80 层的剑完全一样 → 高层掉落无优势，玩家无刷高层动机
- B（等级变体）：需建「玄铁剑·凡/精/绝」三个独立条目 → 内容量 ×3，每个变体要单独配图配文
- **C（物品等级）** ✅：一个条目 + 一个整数字段 → 内容量不变，纵向成长照旧；且 `itemLevel` 是纯整数，符合 Round 19"可量化的一律数值化"

#### 「境界提供基础数值与门槛（解锁秘境/底材）」释义（用户提问）

这句话（出自 `ADR-0005:2`）有**两个独立含义**：

1. **基础数值**：角色**裸装**时的强度来自境界。不穿装备，境界 5 也比境界 1 强；装备是在此基础上做乘法。
2. **解锁门槛（gating）**：境界决定能接触哪些内容——

| 境界 | 可进秘境 | 可掉底材 |
|---|---|---|
| 不入流 | 黑石矿 | 粗铁剑、布衣 |
| 二流 | 黑石矿、竹林 | 精钢剑、皮甲 |
| 绝顶 | 全部 | 玄铁剑、软猬甲 |

⚠️ **两个维度不要混**：
- **秘境层数** → 决定掉出来的装备**有多强**（itemLevel，深度）
- **境界** → 决定能进哪些秘境、哪些底材进入掉落池（gating，广度）

### 23.4 词缀标签化（Q53 相关，用户提问要求举例）

**反对：权重表**（每个底材列全部 20+ 条词缀权重，新增词缀要回头改所有底材，20 底材 × 60 词缀 = 1200 个数字）

**推荐：标签化**

```json
// 底材只声明偏好
{ "id": "base-heavy-sword", "preferredTags": ["力量", "破甲"] }

// 词缀自己带标签
{ "id": "affix-strength",    "tags": ["力量"] }
{ "id": "affix-armor-break", "tags": ["破甲"] }
{ "id": "affix-heavy-hit",   "tags": ["力量", "破甲"] }
{ "id": "affix-fire-damage", "tags": ["火系"] }
```

**权重计算**（建议 `权重 = 基础 × (1 + 匹配标签数 × 加成)`，加成 1.0）：

| 词缀 | 标签 | 匹配数 | 重剑掉落时权重 |
|---|---|---|---|
| 力量 +X | 力量 | 1 | 10 × 2 = 20 |
| 破甲 +X% | 破甲 | 1 | 10 × 2 = 20 |
| 重击 +X% | 力量+破甲 | 2 | 10 × 3 = **30** |

⚠️ **需定细节**：多标签匹配时权重叠加方式。建议 `基础 × (1 + 匹配数 × 加成)`（温和，不出现 ×9 失控值），而非相乘。

### 23.5 特色词缀 = 机制改变型（Q54，用户按推荐采纳）

- **C. 机制改变型词缀** ✅ ——不是数值，而是改变机制（如"你的中毒会传染"）

## 二十四、Round 24：底材分层的修正 + POE 长期成长调研

### 24.1 助手方案被修正：底材不该"一个条目 + itemLevel"

**用户原话**："低等级冒险掉落的装备与高等级冒险掉落的装备，**不光要在数值上区分，更要在文本描述和美术上区分**。所以 3 层产出的玄铁剑不能出现在太高的层级，甚至只限定在 5 层以下就可以，品阶也不可能超过三阶，再往高就要换其他更牛逼的名字了，品阶范围也缓缓逐步提高。这段话只是举例，不是要求，具体怎么做要看本项目实际情况。"

**我错在哪**：Round 23.3 推荐的方案 C（一个底材条目 + 掉落时附 `itemLevel` 整数）只解决了**数值**区分，**没解决文本与美术的区分**。而后者对装备的"身份感"恰恰更重要——玩家记不住"玄铁剑(itemLevel 80)"，但记得住"天外陨铁剑"。

**修正后的模型 = 底材分层**：

```
底材条目（每个独立）：
  ├─ 名字 / 描述 / 美术    ← 各自不同
  ├─ 槽位
  ├─ 固有词缀
  ├─ 偏好标签
  ├─ 层数区间（哪个层数段会掉落）  ← 新增
  └─ 品阶范围（能出哪些阶位的词缀）  ← 新增

掉落时：
  ① 按秘境层数筛选可用的底材池
  ② 从池中选一个底材
  ③ 掷稀有度 → 词条数
  ④ 抽词缀（受底材偏好标签影响）
  ⑤ 每条词缀掷阶位（受【底材声明的品阶范围】限制）
  ⑥ 掷数值
```

**举例（仅为示意，非定案）**：

| 底材 | 层数区间 | 品阶范围 | 文本与美术 |
|---|---|---|---|
| 玄铁剑 | 1–5 | T1–T3 | 粗朴铁剑 |
| 玄铁重剑 | 6–15 | T2–T5 | 厚重阔身，剑脊带血槽 |
| 天外陨铁剑 | 16+ | T3–T7 | 剑身隐有星纹流转 |

**`itemLevel` 还需要吗**？
➡️ 建议 **MVP 不需要**——底材分层 + 品阶范围已足够表达纵向成长。保留 `itemLevel` 作为**可选乘数**（默认不启用），将来若要做"同一底材的层内微调"再开。

**注意**：这与 `ADR-0005:2`"境界提供门槛（解锁秘境/底材）"**完全吻合**——境界/层数决定哪些底材进入掉落池，本来就是这么设计的，是我在 Round 23 把它简化成了 itemLevel，才丢了文本与美术的维度。

**美术侧的一致性**：`ADR-0003:8` 已定"资产按约定路径引用（`assets/icons/<集合>/<id>.png`）"——底材分层意味着每个底材**一个独立 id + 一张独立图标**，这套约定天然支持，无需改动。

### 24.2 POE 长期成长调研（用户："长期成长是换构筑还是加数值，我觉得两个都要，具体可以调研流放之路"）

**结论：POE 确实是两条并行线，而且你的第 1 点（底材分层）正是 POE 的做法。**

#### A. POE 的底材就是分层的（印证 24.1）

POE 的武器底材按等级分档，**每一档有自己的名字、基础属性、等级要求、美术**：

> Rusted Sword（锈蚀剑，Lv1）→ Copper Sword（铜剑）→ Sabre（军刀）→ Broad Sword（阔剑）→ … → Jewelled Foil（宝石细剑，高等级）

**不存在"一把 Rusty Sword 掉在 Lv80 区域变成极品"这回事**——高级区域掉的是**另一个底材**。这正是用户 Round 24 说的"再往高就要换其他更牛逼的名字"。

#### B. POE 的长期成长 = 数值线 + 构筑线，两条并行

| 线 | 机制 | 作用 |
|---|---|---|
| **数值线** | 底材分级（基础属性提升）／词缀阶位（T1 最高，**受 item level 限制**）／品质（quality，+20%）／技能宝石等级 | 让你**能打更高级的内容** |
| **构筑线** | 技能链接（support gem）／**独特装备的机制改变**／升华 | 让你**能用不同方式打** |

**关键洞察**：POE 的**构筑定义主要来自机制改变**（独特装备改变技能行为，如 Facebreaker 让徒手伤害爆增），**数值成长只是让已有构筑更强**。

这与我们已定的设计一一对应：

| POE | 我们 |
|---|---|
| 底材分级 + 词缀阶位 | 底材分层 + 品阶范围（24.1） |
| 独特装备的机制改变 | **机制改变型特色词缀**（Q54 方案 C，Round 23.5） |
| 技能链接 | 主辅有序组合（Round 3）+ 七系 |
| 升华 | 境界突破时的偏向选择（Round 15.1） |

**所以"两个都要"在我们的设计里已经是事实**，只是此前没被明确说出：
- **数值成长**：底材分层（换更强的底材）+ 词缀阶位（刷更高阶的词缀）
- **构筑成长**：机制型特色词缀 + 七系主辅组合 + 兽的机制放大器

两者相互促进：数值让你能进更高层 → 更高层掉更好的底材与机制词缀 → 新词缀开启新玩法 → 新玩法需要新配装。

#### C. 对洗练上限的影响（回扣 Round 23.6）

用户 Round 23 的判断"决定上限的是最稀有的词缀，低层装备洗不出高层数值"——**在底材分层模型下更加成立**：底材条目声明了自己的品阶范围（如玄铁剑只有 T1–T3），所以它的天花板**在数据上就被锁死了**，洗练再多次也出不了 T5。

### 24.3 需要提醒的内容量代价

底材分层意味着底材条目数 = **槽位数 × 层级段数 × 每段变体数**。粗算：

| 配置 | 算式 | 底材条目数 |
|---|---|---|
| 精简版 | 6 槽位 × 3 层级段 × 1 变体 | 18 |
| **MVP 选定（宽松版）** ✅ | **6 槽位 × 3 层级段 × 2 变体** | **36** |
| 完整版 | 6 槽位 × 5 层级段 × 2 变体 | 60 |
| 完整版（多） | 6 槽位 × 5 层级段 × 3 变体 | 90 |

**每个条目都要 7 样内容**：名字、描述、`assets/icons/equipment/<id>.png` 图标、固有词缀、偏好标签、层数区间、品阶范围。
→ 36 个底材 = **252 项内容**；90 个底材 = 630 项。

**因子释义**（用户 Round 24 要求举例说明）：
- **槽位**（6）：兵器 / 冠 / 甲 / 腕 / 腰 / 靴
- **层级段**（3）：秘境层数的分段，如 1–5 / 6–15 / 16+
- **每段变体数**（2）：某段某槽位有几种底材可选

单看兵器槽（3 段 × 2 变体）= 6 个条目：粗铁剑、木剑 / 精钢剑、玄铁剑 / 天外陨铁剑、软剑。六槽皆然 → 6 × 6 = 36。

➡️ **MVP 定为 36 个**（用户 Round 24 拍板，取宽松版）。与 Round 21 的"MVP 3 个秘境"、Round 14 的"MVP 3 个门派"、Round 11 的"MVP 2 只兽"是同一套策略——**验证结构优先于堆量**，层级段与变体数后续按内容节奏扩充。

### 24.4 方法论：「形状」与「逻辑」必须分开评估（Round 24 新发现）

**起因**：助手在 B.2 把五个待定小项笼统标注为"不影响引擎"，用户追问"**你确定不影响引擎吗**"——这个质疑是对的，助手的说法**过于笼统**。

**核心区分**：

| | **形状（shape）** | **逻辑（logic）** |
|---|---|---|
| 是什么 | 存档结构、抽象层次、扩展点、枚举契约 | 具体业务规则的实现代码 |
| 改了的后果 | **动架构 + 数据迁移** | 只改一个函数／模块 |
| 典型例子 | 事件流字段、primitive 契约、效果实例的运行时状态、有序集合的 id 化 | 离线致死判定用哪条规则、掉落权重怎么算、波次调度怎么排 |
| 成本量级 | 高（不可逆或迁移成本高） | 低（可封装成可替换的策略函数） |

**为什么这条区分重要**：
- 形状问题必须**现在定**，因为后补要迁移
- 逻辑问题**可以后定**，只要它被封装成一个可替换的策略边界
- 因此评估一个待定项时，**先问"它动的是形状还是逻辑"**，再决定紧迫程度

**推论**：一个"逻辑"问题若要变成"形状"问题，通常是因为它**没有被封装**。所以引擎设计的一条隐含要求是：**凡是可能变化的业务规则，都要留一个可替换的边界**（策略函数 / 配置表 / 钩子），这样它就永远是"逻辑"问题而不会升级成"形状"问题。

### A.3 架构原则（用户硬性要求）

1. **引擎零题材词汇**：引擎只认 primitive（`damage-over-time` / `stat-modifier` / `rate-modifier` / `crit-modifier` / `dodge-modifier` / `armor-modifier` / `action-lock` / `visual-flag`），永不读 `displayName`。
2. **效果 = primitive 组合 + 参数**，声明式，走 ADR-0005 三层管线（固定值 → 加法百分比 → 乘法区）。
3. **primitive 参数用通用结构**：`amount` / `duration` / `targetSelector` / `condition`。
4. **所有可编辑项暴露**：ticks、dispellable、resistance、expiry、stacking、onDeath 全部是数据，参数 schema 在 config，编辑器据此自动生成表单。
5. **加系/删系/加组合/加效果（用现有 primitive）都不动引擎**；加新伤害模式才注册新 primitive。
6. **不为未做的系统预留 schema**（ADR-0004:7 扩展留白精神）。

### A.4 primitive 初始集合（8 个，MVP 用 5 个）

`damage-over-time` / **`instant-damage`** / `stat-modifier` / `rate-modifier` / `crit-modifier` / `visual-flag` / `dodge-modifier`（**MVP 使用**）
**`heal`** / **`dispel`**（**Round 15 补**：治疗回复与驱散状态。与 `instant-damage` 同族——都是"对某目标施加一次效果"，加进来不破坏结构）
`armor-modifier` / `action-lock`（**MVP 只注册不使用**，作为抽象层压力测试）

> 注 1：`dodge-modifier` 因 Q26（闪避进 MVP）从"只注册不使用"**提升为 MVP 使用**。它同时承担两个方向：提高己方闪避、降低目标闪避（负向值，土/木/水压制手段）。
>
> 注 2：**`instant-damage` 是 Round 10 补的关键 primitive**。此前"攻击造成伤害"被当作战斗默认行为未建模，导致"立即伤害"在 primitive 层缺失。补上后四个用法共用一套代码：普通攻击（target=敌方）／自伤（target=自身）／反伤（target=攻击者）／溅射（target=相邻）。
>
> 注 3：primitive 参数统一用 `amount` / `duration` / `targetSelector` / `condition`（Round 3 用户确认）。

### A.5 出招与战斗文本

- 出招 = 加权轮盘（intent 源可插拔，见 A.8）；MVP 4 个调制器：冷却 / 内力 / 重复衰减 / 系别亲和
- MVP 一个招式 = 一个条目，**不做多形态**
- 一个招式配**多条文本变体**，随机抽
- 招式文本 = 基础模板 + 系别意象词库（可选槽位）
- **槽位语法 = `{attacker}` 英文花括号（非 xkx 的 `$N`）**
- **槽位全集 9 个**：`{attacker}` `{defender}` `{move}` `{weapon}` `{defenderWeapon}` `{limb}` `{damage}` `{consequence}` `{elementFlavor}`
  - 已删：`{动词}`（应为模板固定文本，槽位化致句式雷同，违 `style-guide.md:46`）、xkx 代词 `$P/$p`（视角是集合级常量）
  - `{elementFlavor}` 无属性时填**中性词，不可为空串**（否则产生"，，"）
- **模板 = 片段序列，非"一句固定话挖洞"**（Round 10 重构）：
  `{opening}{attacker}{moveIntro}「{move}」，{weaponAction}{elementFlavor}，{weapon}{verb}{defender}的{limb}，{consequence}。`
  新增片段：`{opening}` 起势、`{moveIntro}` 招式引出、`{weaponAction}` 兵器动作、`{verb}` 动词
- **片段序列可变长度**：模板自己声明用哪些片段（`segments` 数组），下乘 3 段、绝学 7 段——兑现 `style-guide.md:32`"绝学招式模板可到 3 句的华丽长句"
- **三层门控**：① 致命度门控（致命部位需 伤害档∈{重,濒死} AND 剩余生命档∈{少,危}）；② 搭配约束（兵器类型→动词池→部位的 `limbs` 白名单）；③ 节奏一致（先定 tempo 档：急/缓/稳，各片段只从同档抽）
- **引擎只需"带约束的词库抽取器"**：给定过滤条件，从池中随机取一条。所有门控/搭配/节奏都是数据。

### A.6 内力（MVP 最小形态）

上限（境界+心法+装备）／招式消耗／战斗中持续回复／零消耗基础攻击（内力见底自动切换）／离线用稳态 DPS 公式 O(1) 结算。
**七系 × 内力差异化留 v2**，但代价设计已定（见 B.1 待确认项）：

| 系 | 内力维度的性格 | 代价 |
|---|---|---|
| 金 | 耗内破防 | — |
| 木 | 寄赖 / **吸内** | 不能吸干（下限 25%）／转化效率 40%／自身伤害 ×0.7／可被「固本」抵抗 |
| 水 | 滋养：回复 / 上限 | — |
| 火 | 倾泻：高耗高爆发 | — |
| 土 | 承载：上限 / 代偿减伤 | — |
| 风 | 轻灵：消耗降低 | — |
| 雷 | 激荡 / **背水**（内力越低伤害越高） | 触发阈值 <30%，加成上限 +50%；门户大开（防御同步下降）、闪避降低、需主动维持低内力 |

### A.7 闪避（Q26/Q27/Q28）

- **只做闪避，不做招架/格挡**（留 v2）。命中判定两级：闪避 → 命中。
- **通用低基调**：基础 5-10%，上限约 40%，递减 `实际闪避 = 闪避 / (闪避 + K)`，K 在 config。
- **闪避只让这一次攻击落空，不跳过回合**（否则高闪避拖成无限战斗）。
- **闪避是纯数值，不是状态** → 不破坏"2 真状态 + 5 纯数值"的平衡。
- **离线结算**：期望值，有效输出 = 原始输出 × (1 − 闪避率)。
- **与风系不绑定**：闪避是通用数值，风系只通过**内容层词缀权重**更容易出闪避词缀，引擎不知情。
- **降低闪避**：`dodge-modifier` 对目标施加负值。土（压）／木（缠，走传染线）／水（滞）三种语义均可。

### A.8 主动释放武功的扩展性（用户硬性要求）

- **core 只认 intent 接口，从不问来源**：`intent = { 谁、用什么招、对谁 }`
- `auto-source`（加权轮盘）是 MVP 唯一的 intent 源；未来注册 `manual-source` 即支持玩家主动释放，**core 零改动**
- **架构维度抽象现在就做**（"谁决定出招"是战斗循环的必然环节，做成可插拔是设计正确）
- **schema 不建议现在加 `activation` 字段**（为不确定功能预留数据字段，违 `ADR-0004:7`）；将来加字段的成本由 ADR-0002 版本化存档迁移承担
- UI 层哑组件（`ADR-0004:12`），未来加招式按钮不改引擎

**判断原则一（用户 Round 10 明确）**：内容可以后补，**形状不能**。凡是"将来加功能需要重写引擎"的地方，现在就要把抽象做出来——即使该功能本身不做。

**判断原则二（用户 Round 17 提出、Round 18 修正）**：**名称与数量都是内容，引擎不得写死**。可以"有几层"，但改了数量不能崩。

**判断原则三（Round 24，引擎设计的硬要求）**：

> **凡是可能变化的业务规则，都要留一个可替换的边界**（策略函数／配置表／钩子）。
> 这样它就永远是"**逻辑**"问题，而不会升级成"**形状**"问题。

这条是从"形状 vs 逻辑"的区分（A.20）推出来的：
- **形状**（存档结构、抽象层次、扩展点、枚举契约）→ 改了要动架构和迁移 → **现在必须定**
- **逻辑**（具体业务规则的实现）→ 改了只改一个函数 → **可以后定**

而一个"逻辑"问题之所以会变成"形状"问题，**通常只是因为它没有被封装**。所以留边界不是可选项，是**防止问题升级的手段**。

**三条原则的关系**：
1. 原则一告诉你**什么必须现在定**（形状）
2. 原则二告诉你**什么不能写死**（名称与数量）
3. 原则三告诉你**怎么保证其余的东西永远不必现在定**（留可替换边界）

**已按此原则识别的边界**：离线致死规则（策略函数）、离线掉落后处理（`lootPostProcess` 枚举 + 参数）、波次调度（config 驱动）、目标选择（三来源优先级）、掉落链（可配置管线）、学习武功条件（A.10 第 13 条）、强度聚合函数（装备评分 / 角色战力共用）。

**具体做法（Round 18 用户方案，已推翻 Round 17 的 id 化）**：
- **等级/档位序列** → 引擎与存档存**数字**，武侠词是 **UI 映射表**。改词、增删档位都只改映射表，**引擎与存档零改动**。
- **有语义的枚举**（七系、品阶、脉、门派、primitive 类型、事件/命中类型）→ **必须有稳定 id**（被内容交叉引用）。**但引擎不得按具体值分支**——分支条件须数据化（Round 19.4），这样增删成员才不用改代码。⚠️ 稀有度不在此列，它可数值化（见 A.17）。

**唯一需要迁移的例外**：改**等级上限**（非改映射）。此时超出新上限的存档要收敛，属 `ADR-0002` 版本化迁移范畴。

**加/删不对称**：加成员安全；删成员需引用完整性检查 + 迁移（A.10 第 12 条）。

**受约束清单**：江湖序列 6 级／显示档位（**Round 18 改为 50 档**）／词缀阶位 T1–T3／伤害占比 4 档／剩余生命 5 档／秘境层数 —— 均为数字 + 映射。
**不适用**：七系／武功品阶／装备稀有度／脉／门派 —— 有语义，需 id。

### A.11 兽（驭兽，非召唤；**本质是装备，不是战斗单位**）

> **Round 13 关键修正（用户提出，助手验证通过）**：兽不参与攻击，**本质上就是一件装备**，区别是它会在战斗文本中有一席之地。此判断推翻了助手 Round 11 的 NvM 方案，成本从 ≈15% 降到 **≈5%**。

- **引擎模型 = 装备条目**：兽 = 一组修饰符 + 一段可声明的叙事片段。引擎**不需要认识"兽"**，只知道"带 narrative 的装备"。
- **战斗仍是 1v1**，不需要 NvM、不需要参与者集合（但集合抽象仍要做，见 A.10 第 5 条）。
- **通用能力推广**：兵器 → `{weaponAction}`、兽 → 兽片段、名剑 → "剑身发出一声清鸣"，**三者同类**，都是"装备在战斗叙事中的投射"。
- **边界（不能做的事）**：① 成为敌人攻击目标；② 有血量、会死；③ 在主人不出招时独立行动。石龟"替你挡下"= 减伤修饰符 + 叙事包装。
- **槽位**：独立**"随从"栏**，不占 6 个装备槽（兵/冠/甲/腕/腰/靴）。
- **形态**：驭兽（真实动物被驯养驱使）。**排除召唤物**（凭空生成，`ui-direction.md:9` 已禁符箓，`style-guide.md:22` 禁修仙语汇）。机关傀儡作第二条线留待门派设计时评估。
- **与七系关联 = 机制放大器模型**：兽不复制该系伤害，而是改造该系核心机制的某个参数（木=扩散／火=引爆／水=延长／金=维持／土=转移／风=缩短／雷=追加）。

### A.15 伤害计算管线（引擎核心，Round 15 定义）

> ⚠️ `ADR-0005:6` 的"固定值 → 加法百分比 → 乘法区"是**修饰符的聚合规则**，**不是**伤害的应用顺序。两者必须分开定义。

| 阶段 | 名称 | 说明 |
|---|---|---|
| 1 | `base` 基础值 | 招式/装备/境界的原始数值 |
| 2 | `+flat` 固定加成 | "火系伤害 +50" |
| 3 | `+add%` 百分比加成 | "火系伤害 +15%"（同类相加） |
| 4 | `×mult` 乘法加成 | "所有伤害 ×1.2"（异类相乘） |
| 5 | `crit` 暴击 | 暴击率判定 + 暴伤倍数 |
| 6 | `source` 攻方修正 | 内功/外功各自走对应防御 |
| 7 | `defense` 守方减免 | 护甲 / 内功防御（百分比递减） |
| 8 | `vuln/res` 易伤抗性 | 目标受伤加深、系别亲和度 |
| 9 | `dodge` 闪避判定 | 0 或 1 |
| 10 | `final` 最终值 | — |
| 11 | `post` 后续触发 | 反伤、吸血、溅射、兽的追加 |
| 12 | `apply` 应用 | 扣血 → **判定致死（拦截点）** → 触发致命保护 |

**每个 modifier 必须声明自己作用于哪个阶段。此管线必须现在定死——后改会让所有已配数值失效。**

### A.17 数值化清单（Round 19 用户要求穷举）

**原则**：一切可量化的东西，引擎里存**数值**，外面保留**可后台修改的映射关系**；映射支持**区间**（多对一，如 1–5 级 → 一档）。

**需「数值 + 映射表」的 12 项**：境界等级／显示档位（50 档）／门派等级／生产活动等级／伤害占比档（轻中重濒死）／剩余生命档（满多半少危）／**稀有度（整数 0–3，其下游规则"词条数"挂在映射项内）**／词缀阶位（1–3）／武功品阶（1–4）／兽成长阶段／装备强化等级（若做）／秘境层数段（可选）

> ⚠️ **Round 20 修正**：稀有度的因果是"**先定稀有度 → 再按稀有度生成词条**"（稀有度是因，词条数是果），**不是**由词条数反推稀有度。装备生成流程见 Round 20.1。

**纯数值、不需映射**：修为／生命／内力／门派贡献／招式冷却／状态持续回合／连击数／秘境层数本体／层内进度／掉落等级／词缀数值／资源数量／战斗 tick／各项纪录／战力聚合值

**映射表结构**（Round 20 扩展）：**key 是数值，value 是一个配置对象**——`label` 只是其中一个字段，下游规则、解锁清单、呈现参数都在同一处：

```json
{ "level": 3, "label": "绝世", "affixCount": { "min": 5, "max": 6 }, "hasSpecialAffix": true }
```

- 区间形式：`[{ min, max, label, ...params }]`，支持多对一（1–5 级 → 一档）
- 表在 `content/config/`，后台可改；**引擎读对象里的字段，永远不读 `label` 做判断**
- 校验器检查：区间无缝、无重叠、覆盖全值域、**下游规则自洽**（如稀有度递增时词条数下限不得递减）

**真正标准（Round 19 精确化，取代 Round 18 的"有语义/无语义"二分）**：不是"有没有语义"，而是 **引擎是否按具体值分支**。稀有度虽"有语义"，但它的规则（词缀条数）在表里，所以可数值化；反之若引擎写 `if (element === "fire")` 就不可扩展。

**必须 id 化的三类**：primitive 类型（引擎按 id 找实现）／内容条目（`content.md:30`）／事件类型与命中类型（引擎按 id 分支，如闪避 = 0 伤害）

### A.18 秘境结构（Round 21–22）

- **层内模型 = 定时波次**（Round 21 Q44 + Round 22 追加提前规则）：
  **触发下一波 = 时间到 OR 上一波清空，取较早者**。即"清完才来"与"定时才来"的并集。
- **四参数**（全在 `content/config/`，后台可改）：`waveCount` 本层波数／`waveInterval` 波间隔／`waveComposition` 每波构成／`maxConcurrent` 场上怪物上限
- **`maxConcurrent` = 技术护栏（12–20），非难度调节**；超出则波次延后而非丢弃
- **随机化分两层**：间隔 `T ± 20%`（节奏）、构成从本层池抽（搭配）；**精英/Boss 不进随机池**。**核心原则：随机性放在节奏与搭配上，不放在难度上**
- **计时器「一炷香」不实现**（Round 21 Q45：不管设计稿）→ 无探索时长/门票系统
- **推荐境界 = 软提示**（Round 21 Q46），非硬门槛；硬门槛只用于"未通关前一层"
- **离线持续推进**（Round 21 Q47 = A）：`单波清怪时间 ≈ 波总HP / 稳态DPS`；`本层耗时 ≈ Σ清怪 + Σ间隔`；`离线可推进层数 = 离线时长 / 平均单层耗时`。推进会在卡住的层停下
- **目标选择三来源**（Round 22）：① 招式自带 `targetSelector`（内容声明）② 玩家策略配置（存档，**离线用此**）③ 实时点击（仅在线）。优先级 ③ > ② > ①
- **intent 三维度独立配置**（Round 22 关键）：`actor`／`skill`／`target` 各自可 auto 或 manual → 纯自动／**半自动（auto 出招 + manual 选目标，用户要的）**／全自动
- **层主**：每 N 层一个（如第 5、10 层），非每层都有
- **秘境解锁**：混合式——前几个链式引导，之后按推荐境界并列开放
- **待落实的 xkx100 建议**：`unlocks: <下一层 id>` 解锁链显式字段 + 适用境界区间字段（供校验器检查连通性闭环与境界段覆盖）

- **MVP 底材规模 = 36 个**（6 槽位 × 3 层级段 × 2 变体），共约 252 项内容

| | **形状（shape）** | **逻辑（logic）** |
|---|---|---|
| 是什么 | 存档结构、抽象层次、扩展点、枚举契约 | 具体业务规则的实现代码 |
| 改了的后果 | **动架构 + 数据迁移** | 只改一个函数／模块 |
| 例子 | 事件流字段、primitive 契约、效果实例运行时状态、有序集合 id 化 | 离线致死用哪条规则、掉落权重怎么算、波次调度怎么排 |

**用法**：评估任何待定项时，**先问"它动的是形状还是逻辑"**。
- 形状 → **现在必须定**，后补要迁移
- 逻辑 → **可以后定**，只要它被封装成可替换的策略边界

**推论**（⚠️ 已提升为 **A.10 判断原则三**，是本项目的**引擎设计硬要求**）：**凡是可能变化的业务规则，都要留一个可替换的边界**（策略函数／配置表／钩子），这样它永远是"逻辑"问题，不会升级成"形状"问题。

三条判断原则合起来构成一个决策体系，详见 A.10：
1. **原则一**——什么必须现在定（形状）
2. **原则二**——什么不能写死（名称与数量）
3. **原则三**——怎么保证其余的永远不必现在定（留可替换边界）

**由此补出的 A.10 第 13 条**：「学习武功」流程需带可配置的条件检查点（即使 MVP 条件恒真）——这是用户质疑"你确定不影响引擎吗"之后发现的遗漏。

**五个待定小项的精确评估与默认取值**：见 Round 24.5。
- 离线致死 → A 离线不死（策略函数封装）
- 门派入门条件 → MVP 恒真（流程留检查点）
- 师父 → 先只留字段
- 江湖序列 → 新秀/好手/高手/名家/宗师/泰斗
